# AGENTS.md

agentos: one desktop window for every coding-agent session. It shows which session needs the owner, the project's GitHub issues as a queue, notes, and each agent's chat. Agents keep running in a hidden tmux when the window closes.

## Hard rules

- Tests and manual checks run in an isolated setup: always set `AGENTOS_TMUX_SOCKET`, `AGENTOS_STATE_DIR`, `AGENTOS_DEV_DATA_DIR` and `AGENTOS_CONFIG` to throwaway values. The default socket holds the owner's live sessions; a test on it has killed them twice.
- Never install the app to `/Applications` or `~/Applications`, never run `make desktop-install`, `install.sh` or `agentos update` against the real home, unless the owner asks. Live sessions' hooks run the installed app's own binary.
- Stop only the processes you started, by their PID. Never `pkill`, `killall` or kill by a name pattern.
- Clean-up code deletes worktrees, and a configured `session_cleanup_command` may delete more. Any change to it ships with tests against throwaway git repos, never a real one.
- Never create a GitHub issue without the owner approving that specific issue.

## How it works

**One binary.** `desktop/` builds a Wails v2 app whose binary is also what the app and Claude start: the hidden `host` and `mcp` commands, so the app, the host and the tools' server are always one version. Run with no command, it is the app; it has no other command, and any other exits with "agentos has no command line". Nothing links it onto PATH; the app passes its own path (`Config.Binary`) to the host and the MCP config, and a thread needs no `agentos` on PATH.

**Sessions live in tmux.** Each agent runs in a tmux server on a private socket (`agentos` by default, `AGENTOS_TMUX_SOCKET` to change). A session's id is `<project key>/<8 random characters, a-z and 2-7>`. Closing the window leaves the agents running; the app finds them again when it starts. The front end shows each thread as its chat; only a shell's terminal attaches to its tmux pane, over `terminal.Service`. A Claude session's pane runs `agentos host --log <chat log> --socket <socket> -- claude …` with the app's own binary as `agentos`: the host runs Claude headless, keeps the session's chat log and serves a unix socket the app gives Claude its messages and interrupts through; the pane shows the host's echo of the chat, and Ctrl-C there interrupts Claude's turn. Each message gets a UUID, which the socket answers with and Claude echoes back (`--replay-user-messages`) when it takes the message in; it may carry PNG, JPEG, GIF or WebP images of at most 3.75 MB each, so their base64 stays under the API's 5 MB. While an approval waits, a message denies each waiting tool with its text, framed by `internal/prompts/denied.md`, as the reason and is not sent as a message. An approval waits until it is answered, Claude withdraws it (`control_cancel_request`, logged as `cancel`), its call has its result, the subagent that asks for it ends or Claude's list of its tasks leaves that subagent out, or Claude exits or a new run starts (`chat.Waiting`, which the host and the chat service share); a turn's end takes none, since a subagent in the background asks past the turn that started it and Claude withdraws the thread's own approval at an interrupt and rejects its call. A subagent's approval names it by its task id (`agent_id`), which the host turns into its Agent call through the open tasks, or, for a subagent Claude waits on, which has no task in the background, through the call the subagent made; and a message that denies only subagents' approvals is logged as the first one's (`agent` set) and starts no turn. The chat shows a subagent's approval after its row, and a message that answers only subagents' approvals as the owner's message where it was written, starting no turn unless one runs. While a turn runs, a message is logged `queued` and written at once: Claude takes it in at the turn's next step, or runs it as a turn of its own after this one, and its echo logs it as the user's, so the host counts as busy until every written message has echoed and its turn has ended. Send now (`send_now`) is an interrupt, after which Claude runs the queued messages without their being sent again. Every interrupt the host writes carries `spare_background_tasks`, so it stops the turn and leaves the subagents and shells Claude runs in the background going, as Esc does in Claude's terminal: without it an interrupt in stream-json mode stops them too, also with no turn running. A message that was queued when an interrupt went out and that Claude's reply to it does not list under `still_queued` leaves the queue, so it cannot keep the host busy, and is logged `unsent`. The first event the host logs for a run, before it listens on its socket or starts Claude, is `start`: the events before it are an earlier run's, also when that run's host was killed before it logged its `exit`. The host is busy while a turn runs, an approval waits, a queued message is still to run or a task Claude runs in the background works. Claude runs a subagent, and a Bash call with `run_in_background`, as a task beside its turn that outlives the turn's `result`: the host logs its `system/task_started` (with `is_backgrounded`) as `task_start` (the call, Claude's task id, its `task_type`, its description and the Agent call of the subagent that started it, which Claude names by its task id), its `task_notification` as `task_end`, Claude's `system/background_tasks_changed`, the whole list of its background tasks that it sends at each change, as `tasks` (which closes an open task it no longer lists, so a missed end cannot keep the thread working, and opens one it lists before its start, by Claude's task id), and a task still open when Claude exits gets a `task_end` with stop `stopped` before the `exit`. Only a subagent's task (`local_agent`) keeps the host busy: Claude counts its own session idle while only shells run, a shell may be a server that never ends, and a task of another kind, such as a monitor, may watch with no end. Claude tells of the end of a task of its own that was not stopped in a turn it starts itself, with no user message, so the host is busy from that end to the turn's `result`, and any output of Claude's own outside a turn opens one too. The `hold` op (`host.Hold`) says whether it is idle and, when it is, holds it: every later send, answer and mode change is refused with `This thread is restarting` until it exits, so a restart that holds the host before it stops it loses no message, and the composer keeps the text of a refused one. The `mode` op (`host.SetMode`) changes Claude's permission mode between turns, to `plan` or `default` only: it is refused with `Change access when the turn ends` while the host is busy; otherwise it writes a `set_permission_mode` control request, waits up to 10 s for Claude's reply, logs a `mode` event with the new mode, and answers with Claude's own error when Claude refuses it. *Edit from here* on a message of the owner's (`RewindFilesOffer` with no wake, then `RewindPreview` once the owner picks the files and `RewindTo`, a settled thread woken first) rewinds the same Claude with no restart through the host's `rewind` op, refused while the host is busy: with the files, which only ever happens in the worktree agentos made for the thread while no other thread, live or asleep, and no shell works there, a `rewind_files` dry run, refused when a file it names is outside that worktree, then the real one, then a `rewind_conversation` control request naming the newest message the log says Claude holds; the host logs a `rewind` event only once Claude says the conversation rewound, also when that answer comes after the host stopped waiting, and takes no message until it does, the chat drops that message and everything after it up to the event, and a Claude that does not know the requests turns Edit off for the app's run. Claude also reports each change of its mode, its own included, on a `system` line of subtype `status` with `permissionMode`; the host logs that as a `mode` event when it is not the mode the log holds last. A reply to a control request of the host's other than the initialize and interrupt replies goes to the request that waits on it and is never logged. An answer to an approval can carry the input to allow the tool with, such as a question's answers; the log keeps that input on the `answer` event, so the chat can show the answers. A `result` that failed gives its `errors` as the `turn_end`'s text, which the chat shows as the turn's error without Claude's `[ede_diagnostic]` lines. A host started by an older build answers an op it does not know with an error, and a message with images sent to it returns an error, since it sends the text and drops the images. The app tags each thread it starts with `@agentos-access`; a tmux session without that tag is no thread of this app and is left out of every list. The chat service (`desktop/chat`) is the app's one subscriber to each live hosted session's host: it reads the chat log once, for the approvals that wait and the seq it ends at, subscribes after that seq, and when the stream ends while the session runs subscribes again after the last seq it had, waiting 100 ms, doubling to 2 s. Every live hosted session has its follower before the app takes its first call; the service checks the set every second, and `ChatWatch` starts a thread's follower when it has none and returns once that follower has read the log. It hands each `turn_end` to the sessions (see below), and each `mode`, with whether the owner allowed an `ExitPlanMode` approval just before it in that turn, to `Sessions.AccessChanged`; at its start, once the host listens or has had 10 s to, it reads the log and hands on the latest `mode` after the log's last `start`, none when that `start` has no `mode` after it, so a change made while the app was closed is followed too and an earlier run's is not. `AccessChanged` maps the mode (`plan` Read, `default` and `acceptEdits` Supervised, `bypassPermissions` Full) and records an access that is lower; a higher one only when it takes a Read thread to Supervised after an approved plan, so a Read thread whose plan the owner approves becomes Write · Supervised, and nothing Claude reports raises a thread to Full, sends `chat:pending` (`{id, pending}`, `pending` null once nothing waits, and holding the tool's `input` unless its JSON is over 64 KiB, when it holds none and `inputTooLarge` says so, so a whole file an Edit or a Write carries is not sent on each change) when the oldest unanswered approval of a session changes, and sends the events of each thread the front end watches, deltas among them, as `chat:<id>` (`{id, events}`), at most one per 33 ms per thread. `ChatHistory` reads the chat log, also of a settled session; the front end watches first, then reads the history, and merges the two by seq, since an event logged in between comes in both. Every other chat op on a settled session fails with `Thread <id> is asleep`; an op the host refuses fails with the host's own reason (`host.Refused`), and one that cannot reach the host with `Thread <id> did not take …`, the cause going to the log. `ChatSend` takes a message's text and up to 10 images (png, jpeg, gif or webp, each at most `host.MaxImage`, 3.75 MB, whose base64 is the API's 5 MB), checks them all before it saves any, saves each as `<first 16 hex of its SHA-256>.<ext>` in the thread's `chat-media/<token>/` and sends their paths; the `user` event's `files` holds them, and `/media/<key>/chat-media/<token>/<file>` serves them. A host too old for images sends the text alone, and `ChatSend` returns that as a notice, not an error.

**The host's stream reports state.** Claude Code runs no hook: the chat service follows each thread's host, and `desktop/chat/state.go` maps each event of its log to the name of the hook that said the same, which `Sessions.Observe` folds into the state file (the app is its only writer) and saves with the seq of the log entry, so a restart takes in each event once: the owner's or the app's message is `UserPromptSubmit`, a tool call `PreToolUse`, its result `PostToolUse`, an approval `Notification` (`permission_prompt`), a turn's end `Stop`, or `TurnError` when it ended in an error, an interrupt among them, and the host's start and Claude's exit `SessionStart` and `SessionEnd`. A thread is idle from its host's start; `system/init` only gives the conversation, the folder, the model and the transcript, which is `<config folder>/projects/<the start folder with every character that is not a letter or a digit as `-`>/<conversation>.jsonl`, with the long-path rule of `agent.Claude.Transcript`. The folder a thread works in comes from each `system/init`, so a `cd` inside a command shows its new folder only at the next `init`, which is the next turn; until then the branch is read in the folder of the last `init`. From the events the app derives the session's state: `waiting` (a permission prompt, a question, or a reply that ends in a question), `working`, `idle` (the user's move) or `settled` (the process is gone; the row stays until deleted, with no time limit). The stream says only that a turn ended, so a hosted thread whose Claude runs a subagent in the background after the turn that started it, or tells of one's end in a turn it starts itself, would show idle: the chat service follows the host's `task_start` and `task_end` and hands the count of those tasks that are not shells, and whether a report turn is still to end, to the sessions (`BackgroundChanged`), which show an idle thread as `working` while either holds, in the row, the project counts, the idle-sleep hold-off and the holding of PR commands, and as `subagents` on its row. An access change refuses such a thread with `Change access when the subagents end`. *Sleep* in a thread's right-click menu (`SettleThread`), stops the tmux session, whose host stops Claude, and Claude its tasks with it, then the thread's servers (see **Servers**); the menu's Sleep then says how many subagents are still working; the app calls a `settled` thread Sleeping, and its chat shows the stop as `Asleep`. Delete, last in every thread's right-click menu and on a settled card, asks first in the confirm modal: `Delete thread "<title>"?`, then `This stops the thread first.` for a live thread, `Its conversation goes, and so does its row. This cannot be undone.`, and `The branch <b> stays.` for a thread with a branch, then the asleep descendants that go with it (`DeletePlan`'s `children`, nearest first) listed under `Its asleep children go too:`, and a checkbox *Also delete its worktree* (*Also delete its <n> worktrees* for more than one), unticked, only when `DeletePlan` counts worktrees agentos made for the thread or its descendants that are on disk and whose clean-up has not finished: the thread's own when no thread outside the family, running or settled, and no shell works in it, and each descendant's but one a fork takes over (below); none at all when the thread's own worktree is shared, since a delete with the box would always be refused. A fork found to take a worktree over gets it only if it is still a fork with no worktree of its own when the delete gets that far. The delete counts and sorts them with the same function, so the box, a refusal and the delete always name the same worktrees; a thread of the family never counts as another in a worktree of it. `DeleteThread(id, worktree)` settles a live thread first, so its host is told, then removes the row, the state file, the evidence and the browser window, waits up to 10 s until the host has logged Claude's exit, and then removes the chat log, chat images, handover, usage mark, temp folder and host socket; a refresh, a wake or a new thread waits only for the settle and the removal of the row, not for the host; the PR watch forgets it, the clean-up log and the event log keep their entries, and the branch always stays. With `worktree` the worktree goes first, by an unforced clean-up with every check in **Clean-up**, and only when no other thread or shell works in it; a worktree kept refuses the delete with `Thread <n> keeps its worktree: <reason>. Untick the box to keep the worktree, or clean Thread <n> up first` (`the worktrees` when the box takes more than one), nothing is deleted, and the row shows the clean-up as kept; when the clean-up put a live thread to sleep before its second checks kept the worktree, the text says `<reason>. It is asleep now. Untick the box …`, and the thread stays asleep. A worktree another thread or a shell works in refuses it with `Thread <n> keeps its worktree: <who> also works in this worktree. Delete it without the worktree` (or `a shell is open in this worktree`), and no clean-up runs. Without it, every worktree of the family stays on disk as it is and its record in `worktrees.json` goes with its thread, so agentos takes it for a human's from then on and never removes it. A thread in the project folder, or whose worktree another thread uses, gets no checkbox, and Delete never touches its folder. A running clean-up refuses a delete with `Thread <n> is being cleaned up; delete it when that ends`, and a descendant that runs refuses it with `Thread <n> has a running child, <title>; stop it first`. Asleep descendants go with the thread, the deepest first, each as the thread does, so no thread is left without the parent that reaches it: with `worktree` every worktree of the family is checked first, as a clean-up checks, and the delete removes none unless every one passes: one kept refuses the whole delete with that thread's own `Thread <n> keeps its worktree: …`, logged and shown on its row, and nothing goes; a running thread that works in a worktree that is to go, its own or a descendant's, is then put to sleep and every worktree checked again (a refusal then adds `Thread <n> is asleep now`, or `It is asleep now` for its own, and any other error from then on adds `Thread <n> is asleep now`); then the worktrees go, the deepest first, and the threads after them; a descendant that works in a worktree of the family, as a child in its parent's folder does, does not keep it. A descendant's worktree that a fork outside the family works in stays on disk, with or without the box, and when that fork has no worktree agentos made for it, the record and marker go over to the fork (of several, the one that started last, then the first by id), so a delete of it with the box can take the worktree; no other thread is given one, since a thread with a worktree of its own would then lose track of it and one that is not a fork works on a branch of its own; such a fork has the record's branch as its clean-up's, and still hears no PR. With the box, a descendant's worktree that a shell or a thread outside the family works in, and that no fork takes over, refuses the whole delete with `Thread <n> keeps its worktree: Thread <title> also works in this worktree. Untick the box …` (or `a shell is open in this worktree`), and nothing goes. A running clean-up of a descendant refuses the delete too. While a delete runs, Wake, Fork and a second delete of the thread or of a descendant refuse with `Thread <n> is being deleted`, and none of them can delegate. A deleted thread never comes back: a refresh, a restart and a late event find no state file; Wake, `ChatSend`, `ChatDraft`, `TypeInto` and Sleep refuse it with `Thread <id> was deleted` until the app restarts, and with `No thread <id>` after; a PR command wakes nothing; and a start of its issue starts a new thread. Delete refuses a shell, and a shell's state file is never read. At each start of the app the events of the run in the chat log after the latest one taken in are taken in, so a turn interrupted while the app was closed ends too: a `turn_end` goes in as a `Stop` so held prompts go out and the turn's usage is recorded, or, with the error flag (an interrupt or an API error), as a `TurnError`, which does the same but raises no reply alert. The state file also keeps the latest 200 state changes, so the row's timeline and the `worked` time of stretches that ended while the app was closed outlive the app; a stretch is recorded once, at the change that ends it. The app writes what it started the session as (title, access, issue, action, model, effort, folder, branch, the thread it was forked from, the thread that delegated to it, its first start `created` and its latest start `woke`) into the state file at start, at a wake and at a rename, and the events keep it, so a session that ends while the app is closed comes back as itself. The stream's working folder never changes the thread's branch. The stream does not carry the final tokens, so the app reads the transcript Claude Code writes: at each event it reads the new lines of it and of its subagents' transcripts and adds their tokens and cost, at the list prices in `internal/usage`, to the row. It records them as one `usage` event per model, for every access, only when the turn is over: a second after the turn's end, since Claude Code may write the turn's last reply just after it, at Claude's exit and when the session is gone. After a restart it starts after the latest usage the event log holds for the session, so it reads again what it had not recorded; it starts each transcript at the offset it saved when it last recorded usage, so it does not read the whole file again. A woken thread keeps its id, so its usage goes on under it from its first start, and each wake records a start event labelled `resumed`. The same read sets the row's model and effort to the newest assistant line's, kept in the tmux session and the state file like the start choice, so the row follows a `/model` change.

**What a session is started with.** Folder: a thread runs where it starts and never moves. An issue thread, whatever its access, starts in a worktree agentos makes for it; a thread with no issue, at every access, starts where the config's `new_thread_place` says, a worktree agentos makes for it when that is unset or `worktree` and the project folder when it is `project`, unless the caller picks a place (`NewThread`'s `place`, `worktree` or `project`; `delegate`'s `where` for a child); the setup session runs in the project folder. The worktree is `<project>/trees/<branch>`, kept out of the owner's `git status` by a `/trees/` line agentos adds once to `<git-common-dir>/info/exclude` (never a `.gitignore`), on the issue's branch (`session_branch_fallback`) or, with no issue, on a branch named from the title: lower case, a `-` for each run of other characters than a-z and 0-9, at most 40 characters cut at a `-`, `thread` when nothing is left, then `-2`, `-3`… while a local or origin branch has that name. A branch that exists, locally or on origin (fetched when this clone has no copy), is checked out as it is and never reset; a new one is made by `session_worktree_command` from the default branch on origin, fetched first, and the worktree is the one git then lists on the branch, wherever the command put it. A branch that a worktree already has checked out runs the thread in that worktree, which agentos does not record and so never removes; one that another thread, live or settled, works on is refused with `Thread <n> works on <branch>`. A project that is not a git repository runs every thread in its folder. Each worktree agentos made is recorded in `worktrees.json` with the base it started from, and marked with the thread's id in its own git folder (`agentos-thread`); a start that fails after its worktree was made removes that worktree, without `--force`, and only while it is still the one agentos made. The branch is tagged `@agentos-branch` and kept in the state file as `branch`; the row's `worktree` is the folder only when agentos made it. Environment: `AGENTOS_SESSION` and `AGENTOS_CONTROL` (the control socket's path), which mark the thread's processes (see **Servers**) and which the app trusts for nothing else, and `TMPDIR` set to its own temp folder, removed at the clean-up or when the thread is deleted, which the Claude provider also sets as `CLAUDE_CODE_TMPDIR`; `MCP_TOOL_TIMEOUT=3700000`, so an agentos tool call may last the hour a `wait` takes; and `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=1` at every start, a fork and a wake too, so Claude keeps a checkpoint of the files each message's turn edits, which a rewind of the files needs. Claude runs with `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --thinking-display summarized --permission-prompt-tool stdio` (without `--thinking-display` its thinking blocks stream with no text; a Claude that fails at its start on that flag, before it writes a line, is started again by the host without it and given what the host had written, the host logs a `start` that names the flag, and the app leaves the flag out for the rest of its run; a refusal an earlier run logged does not count), with the thread's access as `--permission-mode` (Read `plan`, Write · Supervised `default`, Write · Full access `bypassPermissions`) and `--allowedTools` with the `gh issue` commands that hand work on, `agent-browser` when it has a browser, and the agentos tools, `mcp__agentos__<name>`: all thirteen for Write and Full, and for Read every one but `show` and `track` (`mcp.ReadNames`). In plan mode Claude still asks for an allowed tool that has no read-only hint, so the host answers an ask for an agentos tool with yes itself and logs nothing, and no approval card shows for it; for `show` and `track` it does so only once Claude has reported a mode other than `plan`, so a Read thread asks the owner for them. Any other tool, also one of another server named `agentos`, asks the owner as usual. At each start and wake the app makes the thread's host a new token, 32 random bytes in base64url, and writes it into `<the id's 8 characters>.mcp.json` (0600) beside the host's socket in its 0700 folder, an MCP config that starts `agentos mcp` with the token in `AGENTOS_MCP_TOKEN` and the control socket's path in `AGENTOS_CONTROL`; Claude gets the file as `--mcp-config`, so the token is in no command line and in no environment but the server's. The app keeps only each token's SHA-256, and when it starts it takes the live threads' tokens from their files. An `orchestrate` call acts as the live, hosted, not deleted thread its token names (`Router.Caller`), never as its `Session` or `Project` field; no token, an unknown one, one from before a wake and one of a settled or deleted thread are refused. Settling or deleting the thread removes its file. The access is tagged `@agentos-access` and kept in the state file as `access`; the owner changes it between turns from the model menu in the thread's composer (`SetAccess`), which is disabled with `Change access when the turn ends` while a turn runs or an approval waits. The app asks the thread's host, not the recorded state, and refuses with the same sentence while the host is busy, so a thread waiting on a reply that asks can change and one that was just sent a message cannot; it refuses a deleted thread and a blank access (`Pick an access level`). A settled thread keeps the new access for its next wake; a live one changes between Read and Supervised through its host's `mode` op, with the same host and Claude, and a change to or from Full holds the host (`hold` op), records the new access, settles the thread and wakes it with it under the same id, resuming its conversation, since Claude takes `bypassPermissions` only from its start; a wake that fails leaves the thread settled with the new access; an access this build does not know, or none, is Read. Claude also gets `permissions.additionalDirectories` for the app's folders, `--model` and `--effort` when something picks them (see `docs/config.md`), and `--append-system-prompt` with the texts in `internal/prompts`: `session.md` (where it runs and the agentos tools every thread may use), then `thread.md` (one text for every access: what Read, Write and Full allow, the branch rules and the `APPLICATION_PROMPT:` rule), `issue.md` for a thread that works on a GitHub issue (its number, at every start and wake), `worktree.md` for a thread that starts in a worktree, also one a human made (the branch and folder, and that the thread never makes a worktree), `fork.md` for a fork (it has no branch of its own and never calls `track`), `child.md` for a child, at its start and at each wake (the title of the thread it works for, that its first message is its task and that its last reply of each turn is its result), `browser.md` when the project has a browser, and `handover.md` with the context another thread passed as the `issue` tool's `prompt`; the session that sets a project up gets only `setup-brief.md`.

**The tools talk to the app.** The hidden `agentos mcp` serves the agentos tools to a thread and sends each call over the control socket (`control.sock` in the state folder) as `orchestrate`, with the token in `AGENTOS_MCP_TOKEN`, which names the thread that acts. The socket answers only `orchestrate`: each service that a tool reaches registers a `Commands` struct on the `desktop/control` router in `desktop/internal/app`, and the router runs those handlers only for a tool call, which sets their session and project from the token (`HandleExternal` registers a command the socket answers; `Handle` one it does not), so a client on the socket cannot name another thread. No command is typed by the user: the app is the only interface.

**Orchestration.** A thread reaches the app through the thirteen tools of its `agentos` MCP server, which Claude names `mcp__agentos__<name>` and whose texts are `internal/prompts/tool-<name>.md`: the six orchestration tools (`delegate`, `threads`, `read`, `send`, `wait`, `stop`) and seven agent tools that do what the agentos commands did, so the agent runs no `agentos` command: `note`, `issue`, `new_thread`, `show`, `track`, `refresh` and `browser`. `orchestration.Commands` answers every call as the thread its token names (`Router.Caller`), never as the request's `Session` or `Project`. An agent tool's input becomes the control request its command sent (`agentRequest`; `new_thread` sends `new`, the others their own name), with `Session` the caller and `Project` the caller's project, and goes through `Router.Answer` to the same handler; an input with a field its schema lacks is refused, so no input names another thread. `new_thread`'s `access` defaults to the caller's and is refused above it (`A thread with <a> access cannot start a thread with <b> access`); `issue` starts the thread with the lower of its action's access and the caller's (an id that is not a running thread starts none; a Read caller starts a Read thread; a Full caller starts a Supervised action's thread as Supervised), and refuses a Full sleeping thread from a thread that is not Full; `show` takes a file only inside the thread's folder, the project folder or the thread's own temp folder, judged after symlinks are resolved (`Sessions.ShowRoots`), and `note` text is at most 64 KB and a `show` caption 1 KB; `show` takes an absolute `file` or a `text`, not both; a `prompt` is at most 6 KB; the MCP server gives a `browser` call 75 s. A child does not show in the sidebar: it is a card in its parent's chat, and its attention rolls up to the parent; one whose parent is gone shows there. A thread starts a child thread with the `delegate` tool, which `orchestration.Commands` answers as the token's thread and passes to `Sessions.CreateChild`. A child is tagged `@agentos-parent` with its parent's id at its start, kept as `parent` in its state file and at a wake, so the link outlives a settle, a wake and a restart; its row's `parent` names the parent, `""` for a thread the owner started, also one started by `new_thread` or `issue`. `CreateChild` checks, in order, that the parent runs; that the child's access does not rank above the parent's (`A thread with <parent's> access cannot start a child with <asked> access`), at every place, so a Read thread never gets a Write child; that the parent is fewer than 3 delegations from a thread the owner started, so a grandchild's child cannot delegate; and that fewer than 8 of its children run. The tool's `access` defaults to the caller's and its `where` to `folder` for a Read child and `worktree` for the others. `folder` runs the child in its parent's folder with no branch of its own: like a fork, it never keeps the parent from tracking a branch there, and `track` refuses it; such a child is refused while a clean-up of the parent runs (`Thread <n> is being cleaned up; start a child in its folder when that ends`); `worktree` makes a new worktree on a branch named from the title, from the commit the parent's folder is at (`session_worktree_command`'s `{base}`), not from origin's default branch; `issue` starts the issue's thread on the issue's branch, and is refused with `Issue #<n> has thread <id>: send to it instead` while the issue has a live or settled thread. A blank title is the task's first line. The task goes to the child's host as its first message, framed by `delegated.md` and marked `APPLICATION_PROMPT:`, before the tool answers, so the child's chat holds it once the parent has the id; the answer is the child's `id`, `n`, `title`, `project`, `access`, `where`, `dir` and `branch`. A child gets no handover and none of its parent's chat. A woken child keeps its own access, and a change of the parent's access (`SetAccess`) waits for a delegation that has checked it to start its child. A call that ended before the start starts no child. The tool's `project` names another project by a configured project's name or key, never a folder; an unknown one is refused with `No project "<name>": the projects are <names>`. There `folder` is that project's folder, `worktree` a new worktree from its default branch on origin (`{base}`'s default), and `issue` that project's issue; the checks are the same, and the child's row has that project and the caller as its `parent`. The app logs each delegation to another project once, naming both threads and projects, since it starts work in a project the owner may not have on screen. Putting a parent to sleep leaves its children running; a delete of it takes the asleep ones (see **Hooks report state**). `ParentOf`, `ChildrenOf` (the direct children that are not deleted), `Descendants` and `AccessOf` answer the other tools' questions about a thread's family. `threads` lists the rows of the caller's project, of a named one or of `all`, with the deleted left out and the caller's marked `you`. `read` pages back through the chat log of any thread that is not deleted: `messages` gives each user message, `from` the owner, `agentos` for an `APPLICATION_PROMPT:` text or the sending thread's id, and each agent reply with its text blocks joined; `activity` adds each tool call as `<tool>: <summary>`, the line an approval card shows (`chat.ToolSummary`), with `error` on a failed one; each text is cut at 2 000 characters and the answer at 40 000 bytes. `send` frames the text with `from-thread.md`, marks it `APPLICATION_PROMPT:` and gives it to `Sessions.Tell`. It is refused to the caller itself and to a thread whose access ranks above the caller's (`A thread with <a> access cannot message a thread with <b> access`), so a thread never has one with more access act for it. `Tell` wakes a settled thread, and the host's `send` op logs the sender as the user event's `from`. While the thread waits on the owner's answer to an approval, the message is held in the queue of a PR's commands and goes once the answer is in, so it never denies the approval: the app holds it when the recorded state says the thread waits or its chat log shows an approval waiting, as a subagent's does after the turn that started it ended, and the host refuses a message with a `from` while an approval waits, which the app then holds too. A message the host refuses while it is held for a restart (`host.ErrRestarting`), as for a change of access, is held the same way, and so is one told while the restart runs, until the thread runs again. Held messages go in order: while the messages held for a thread are being sent, a new one is held behind them. A held message outlives a settle, which wakes the thread for it. One for a sleeping thread that is being cleaned up waits for the clean-up to end, at most 30 s, and then wakes it; one for a thread that is deleted or is being deleted is dropped, and the app logs it; a quit of the app drops them all. The rank rule is checked when the message is told, under the lock an access change takes, and again when a held message goes: one whose sender now has less access than the thread is dropped, and the app logs it. `steer` sends the message and then Send now, and the host logs the sender as that interrupt's `from`. `stop` reaches only the caller's descendants (`Thread <id> is not a child of this thread`): it interrupts the open turn of that thread and of each of its own descendants, and the host logs the caller as the interrupt's `from`. It drops the messages held for each thread it stops, so none of them starts a new turn for one once its approval ends, but a child's result, which it keeps for that thread's next turn, and answers the threads it stopped and how many messages it dropped. `wait` answers one slice of at most a minute (`slice_ms`; the `agentos mcp` server calls it again until `timeout_seconds` passes and gives Claude only the last answer's `text`). It is refused on the caller itself and on any of its ancestors (`Thread <id> started this thread; waiting on it would wait forever`). The thread is done when its chat log's last `turn_end` comes after its last user message, no queued message waits to be taken in, no message a thread told it is held for it (`Sessions.HoldsTold`), no subagent works in the background (`Task.Works`) and no turn that tells of the end of a task of Claude's own is still to come, and at once when it has settled or was deleted; the answer is `{done, text}`, with `text` the last reply after the last user message, cut as `read` cuts it, or a sentence that says how the thread stands: its turn failed or was stopped, it settled, was deleted or still runs, or waits on the owner's answer to an approval. Until then the slice waits on `Chats.AwaitTurn`, which the thread's follower answers at each `turn_end` it takes, after telling the sessions, and with `chat.ErrThreadGone` when Claude exits or the follower stops (the thread settled, was deleted or its host died, or the app quits); the slice also ends when the caller's own turn ends, as at an interrupt, or the caller stops running. `Commands.Waits(waiter, thread)` is true while a wait lasts: from its first slice until a slice answers it done, the waiter's log has a `turn_end` after the seq it had when the wait began or the waiter no longer runs, or the deadline the `agentos mcp` server sends (`until_ms`, at most an hour on) passes, so it holds between slices too and ends when Claude cancels the call between two of them. A child's result goes to its parent: at each `turn_end` a follower takes, and at the exit it takes when the thread settles, also one already in the log as it starts, `Chats.OnTurnEnd` hands it to `Commands.ChildTurnEnded` after the sessions; a thread that stops running with no follower to take its exit, and one the app finds asleep as it starts, as when it settled while the app was closed, reach `Commands.ChildSlept` through `Sessions.OnSlept`, the ones found asleep one after another; it reads the child's log once and hands a result still to give, with what it read, to the same queue as `ChildTurnEnded`. When the thread is a child, the seq that ends its last turn (the `turn_end` after its last user message, or the exit when the owner put it to sleep before the turn ended) comes after the seq `reported` holds in its state file and the turn is done by `wait`'s rule, the result goes once, one child at a time and in order. It goes to the parent's `wait` on the child when one is in flight (`Waits`, or a slice that answered with that turn), else through `Tell` as `child-done.md` (`child-later.md` once a result went before) from the child, marked `APPLICATION_PROMPT:`, which wakes a parent that sleeps and is sent whatever `session_prompt_send` says. A parent asleep with a clean-up due or running (its PR merged or closed and the clean-up waiting, running or blocked) is not woken: the result is held as one a stop kept, does not block the clean-up, and goes at the parent's next wake. Since the PRs are known only once the app has looked at them, a result for a sleeping thread waits for that first look after a start. Its outcome is `completed`, `failed: <error>`, `was stopped by the owner`, `was put to sleep by the owner` when the owner's sleep (`SettleThread`) made the exit, which the host logs with `chat.ByOwner` as its text, or `was put to sleep` for the app's own, as at a PR's end, a clean-up or a project's removal, and its result the child's last reply, cut as `read` cuts it, with a line on `read` when it was cut; a turn a thread stopped with `stop` gives none. The parent's log keeps the bare reply as the user event's `body` and marks it `result`, as `send` keeps its bare text as `body`; the chat shows `body`, takes `APPLICATION_PROMPT:` off every message it shows and makes only a marked message a child's result card. The wait and the message each claim the result before they give it, so the parent gets it once, and a delete of either thread drops its claims and its waits (`Sessions.OnDelete`): a slice that answers done after the message claimed it, or after `reported` covers it, answers `{done: true}` with `Thread <id>'s result of this turn is sent to you as a message instead.` A result held for the parent counts as given only once it goes (`Told.Done`), so a quit of the app before then sends it at the next start. A `stop` of the parent keeps the result held for the parent's next turn: it starts no turn and wakes no thread, and goes once `Sessions.NextTurn` says the parent took a message or started a run, which its follower says at each user message and run start and when it starts, and a delete of the child drops it; one the parent cannot take, as when its wake is refused, goes again after 1 s, doubling to a minute, while the parent exists and the child is not deleted. Then `SetReported` records the seq, and the child goes to sleep through `SettleIdle`, which settles it only while its host is idle and holds what it is told meanwhile until it sleeps, unless a task of its own, as a shell, is still open: that task's end runs a later turn, whose result goes as a later one. A message wakes a child that sleeps, and each of its later turns' results goes as a later one. A child's reply raises no `replied` alert, since its parent reads it; its `waiting` still does.

**The front end talks to Go through Wails.** Each `desktop/<pkg>` binds one `Service`; React calls `window.go.<pkg>.Service.<Method>(...)`, which returns a Promise, and listens with `window.runtime.EventsOn(name, handler)`. `desktop/frontend/src/api.ts` wraps every call and `types.ts` mirrors the Go structs; the Go side is the reference. A failing method rejects with a short sentence for the user; empty lists are `[]`, never `null`. Lists of one project arrive as `{project, items}` events: drop one whose project is not the current one. A thread's chat events are named `chat:<id>`; `chatEvent(id)` in `api.ts` gives the name its type. A shell's output is no event: once `TermOpen` returns, the front end reads it as raw bytes from `GET /term/<id>` (`terminal.Handler`, served beside `/media/` by `App.Assets` in the window and in the browser mode), one response per terminal that ends when the shell exits or its terminal closes; a second read ends the first and gets the screen painted again. `window.go` is missing under plain `vite dev`, and the front end runs on `mock.ts`. With `AGENTOS_HTTP=127.0.0.1:PORT` the binary serves the real front end in a browser, with a shim that turns calls into `POST /__call/<pkg>.Service/<Method>` (header `X-Agentos: 1`) and events into the stream `/__events`; it answers only its own listen address.

**The queue.** `issues.Service` lists the current project's open issues through `gh`, grouped by the project's `queue_sections`. Starting an issue opens a thread with the access its action sets (`access: read|supervised|full`, Supervised by default; a config whose action still sets the old `kind` does not load), titled `#<n> <title>` with the action's name as a badge, starts claude with the model and effort the action and the issue's `model:`/`effort:` labels pick, then sends the action's command: Claude's host gets it as a message once its socket listens. With `session_prompt_send: manual` the command is left as a draft in the chat. An issue has one thread, whatever its access: one with a live thread gets it back with nothing sent, whatever action is started, also when two starts come at once; one whose thread has settled (and is not deleted, ran under a host and is not a fork) gets that thread woken, with its own access, a handover given to the start in place of the one it had, and sent the action's command; an issue missing from the cached list has the list read again once. *Set up project* in a project's right-click menu on the rail runs `SetUpProject` for that project: for a project with no `queue_sections` it fills a basic block (`project.SetUp`), then it starts a Supervised session briefed to write the repository side; one that has queue sections keeps its config and only gets the session. `DismissSetup` still saves `setup_dismissed`, but no part of the UI calls it any more.

**Pull requests.** Every thread with a branch follows its branch and PR, whatever its access. A thread's branch is the one agentos made its worktree on or the one it reported with `track`, and nothing else: the folder it works in never adds, takes or changes it, and a thread with no recorded branch (one in the project folder that never called `track`, a fork, or one started before agentos recorded branches) has no PR and no clean-up. No two threads have one branch. `track` refuses a fork, a Read thread (`A Read thread works on no branch`), the default branch and a branch another thread has (`Thread <n> works on <branch>`); it tags the branch `@agentos-branch` and keeps it in the state file, and when the thread's own worktree has that branch checked out, its record in `worktrees.json` follows; then the app looks up the branch's PR. The app fetches every tracked PR every minute. Between those, each project with a session on a branch has a watcher: `gh webhook forward` by default, falling back to polling the PR list every `pr_poll_interval` with `If-None-Match`. A thread's turn end also looks its branch's PR up at once, so a PR opened during a turn shows when the turn ends. Each fetch also reads with git where the session's branch stands: commits not on origin (not on the base when origin has no copy), uncommitted files, commits ahead of and behind the base on origin, and after a merge the commits the merged PR did not take; each `PostToolUse` reads it again, so the row follows the agent's work. A new comment or review that is not an approval, by anyone but the gh user, types `pr_review_command` into the session (each reply in a review thread is a review of its own), but not while the PR is a draft unless `pr_review_drafts` is set; failing checks on a new commit type `pr_checks_command`; a new commit that conflicts with the base types `pr_conflict_command`, found at the one-minute fetch, since a base that moves does not touch the PR. Claude gets each command as a message through its host, or as a draft in its chat at once when `session_prompt_send` is `manual`. A session that is working or waiting on the owner gets each command held for it once, in order, when its turn ends; a session that ends first, settled or cleaned up, loses them. A settled issue thread is woken for it (see **Waking**), then gets the command, sent unless `session_prompt_send` is `manual`; a thread whose issue has another live thread stays settled, and so does a settled thread with no issue. Prompts held for a thread that settles by itself go out after it wakes; a thread the owner or a clean-up settled loses them.

**Waking.** A settled thread that ran under a host wakes under its own id: *Wake* on its card or in its right-click menu (`WakeThread`), a message or a draft from its composer (`ChatSend` and `ChatDraft` wake it first), a PR command, or a start of its issue. `Sessions.Wake` starts a tmux session with the same name in the folder the thread started in, under a host that goes on with the same chat log at the same socket, so the chat's numbering has no gap, with `claude --resume <conversation>` when it has one, and the thread's model, effort, handover, browser and fork tag. The thread keeps its row, number, state file, history, usage and branch; `created` stays its first start, `woke` and the row's `wokeAt` move to the wake, and a PR that merged or closed before the wake is an earlier wake's. The wake also lifts a clean-up's mark, so its next PR is watched, settles it and is cleaned up. A thread whose worktree agentos made is gone, as after a clean-up, gets it back before Claude starts, at the same path on its branch, with every commit: git's stale entry for that path alone is dropped (never a repository-wide `git worktree prune`), then `git worktree add` of the local branch, else `-b` from `origin/<branch>`, never `session_worktree_command`; it is marked and recorded again. The wake fails, the thread stays settled and the record is unchanged when a folder that is not the thread's worktree is at the path (`<path> exists and is not this thread's worktree`, and agentos leaves it as it is), when another worktree, there or gone, has the branch checked out (the error names it), or when neither this clone nor origin has the branch (`<branch> is gone, so thread <n> cannot get its worktree back`). A wake is refused while a clean-up of the thread runs (`Thread <n> is being cleaned up; wake it when that ends`), and a thread whose folder is gone and not restored, such as a fork whose source's worktree was removed, does not start (`<path> is gone, so this thread cannot start there`). 

**Forks.** *Fork from here* on a reply of a thread that runs, or ran, under a host calls `ForkSession(id, at)`, where `at` is the uuid of the reply's last block, and selects the new thread. Claude starts with `--resume <conversation> --fork-session --resume-session-at <uuid>`, so the fork continues the conversation up to that reply under a new id. The fork is titled `<title> (fork)`, has the thread's access, issue, model, effort and handover, and starts in the folder the thread runs in, its worktree too, since Claude finds a conversation by its folder, with no branch of its own. Before the fork's host starts, the app writes the fork's chat log: the thread's events up to that block, without drafts, queued or unsent messages and the thread's run starts, then a `turn_end` at the block's time; it copies the images those events show into the fork's `chat-media/<token>/`. On a message of the user's, the fork continues from the reply before it and gets the message's text as a draft in its composer. A thread with no conversation yet cannot be forked. A fork is tagged `@agentos-fork` with the thread's id, kept in its state file and at a wake, and its row's `forkOf` names the thread. Its issue is only shown: it claims no branch, `track` refuses it, it is never the issue's session for the queue, a start or a wake, and it hears no PR. A live fork runs in its thread's folder, so it keeps that thread's worktree from a clean-up with `Thread <title> also works in this worktree`, as any other live thread does that runs in it or whose last reported folder is it; a forced clean-up goes ahead, and a settled fork keeps nothing. A fork, and a new shell for a thread, is refused while a clean-up of that thread runs (`Thread <n> is being cleaned up; fork it when that ends`, `…; open a shell when that ends`). A uuid or a conversation Claude cannot find ends the fork's first turn with `error_during_execution`, and the chat shows Claude's reason.

**Clean-up.** Clean-up frees disk: it removes only the worktree agentos made for the thread, and the branch always stays. When the PR of a thread's branch merges or closes, the thread settles, whatever the clean-up mode; one whose turn runs, also while it waits on the owner for a permission or a question tool, settles once that turn ends, and only then is cleaned up, and the PR commands held for it are dropped; a reply that ends in a question has ended its turn. When the PR merges (`auto` by default) or closes (`manual` by default), the app cleans up: the checks first (a worktree in the middle of a rebase, changes or new files in it, commits on its HEAD that no ref on origin holds and the merged PR did not take, prompts held for the thread (`messages wait for this thread`), a running turn, also one that waits on the owner for a permission or a question tool (`a turn is running`), another live thread that runs in it or whose last reported folder is it (`Thread <title> also works in this worktree`), a shell open in it (`a shell is open in this worktree`) or a shell of the project in a folder tmux does not know (`a shell whose folder is unknown is open`), or a worktree no longer on the thread's branch keeps it, with the reason; so does a failed fetch of origin or a list of shells tmux cannot give), then it settles a live thread, runs the checks again, since the agent may have changed the worktree until it stopped, runs `session_cleanup_command` (default `git worktree remove {force} {worktree}`) through `sh -c` in the project folder, then removes the thread's temp folder and closes its browser window; its row, state file, chat log, images, evidence and branch stay. The command runs once per worktree, on the folder recorded in `worktrees.json`, and only while that folder still holds the worktree agentos made for the thread (the newest record at the path is the thread's and not removed, and the worktree's `agentos-thread` marker names it): never on the project folder, git's main worktree, a folder holding either, a worktree a human made (also one at a path agentos used before) or one a thread only ran in, forced or not. Before each step after the settle, just before the command and at the end, the app checks that the thread has not woken since the clean-up settled it, and stops, keeping what is left, with `Thread <n> woke during the clean-up` if it has, so a woken thread keeps its worktree, temp folder, browser window and PR; `CleaningUp(id)` says while a clean-up runs. The worktree counts as removed once git no longer lists it and its folder is gone, whatever the command's exit code, and a worktree whose folder is gone already counts too; its record then says `removed`, and no clean-up runs on it again. A command that fails and leaves it keeps it with `the clean-up command failed: <first line>`, and one that exits 0 and leaves it with `the clean-up command left <path>`. A thread with no worktree agentos made, or one removed already, loses only its temp folder and browser window; `manual` still asks first, since the app never cleans up by itself then. A kept worktree leaves the row `blocked` with the reason; the user can force it, which skips the checks but never the rules on what agentos made. The row's *Clean up* after an ask runs every check; only *Clean up anyway* on a kept row forces, and its confirm names why the worktree was kept; a kept row also offers *Clean up now* in its right-click menu, whatever kept it, which runs every check again. A clean-up the checks kept after the PR of a settled thread's branch merged or closed since the thread's latest start is tried again, with every check, every hour (`SetCleanupSweep`, where 0 turns the sweep off), and at each start, when `session_cleanup_mode` cleans that PR up by itself (`auto`), by the first look at the PRs, since what a clean-up tried is not kept over a restart, while under `manual` the ask comes back after a restart and stays an ask; an ask, a clean-up that runs, and a thread that runs again, as after a wake, are left alone. A try that keeps it for the same reason as before logs nothing, in `cleanups.json` or the event log; a new reason or anything removed logs as usual. *Clean up now* (`Cleanup(id, false)`, at once, with every check) is in the right-click menu of every kept row, and of a thread whose worktree agentos made is still there and whose clean-up neither runs nor asks. While a delete of a thread runs, any clean-up of it but the delete's own is refused with `Thread <n> is being deleted`. While a wake of a thread runs, from its first check until the thread runs, every clean-up of it is refused with `Thread <n> is waking; clean it up once it runs`, and a sweep that finds the thread running again stops (`Thread <n> runs again`): each marks itself before it looks for the other, so a clean-up never removes the worktree a wake restores and starts Claude in. A clean-up that finished is not run again for that thread, also after a restart (`cleaned` in `prs.json`), and the row shows no PR. A PR that merged or closed before the thread last started, at its first start or its latest wake, is an earlier thread's, or an earlier wake's, and is ignored, unless the owner was asked to clean up after it and has not answered: that ask outlives a wake and a restart (`asked` in `prs.json`), and it settles nothing. `session_cleanup_mode` picks whether a merged or closed PR is cleaned up at once or asks first (`cleanup: 'ask'`), so a PR that opened and merged while the app was closed is cleaned up at the next start. A child that goes to sleep, by Sleep, a stop or by itself, but not for a change of access or a delete, loses its worktree at once when that loses nothing: agentos made the worktree for it and it is still that worktree, and the checks above pass, with an asleep thread in it, as a fork, counting too, and so does any shell of the child's own, idle or busy (`a shell of this thread is open`): this clean-up never closes a shell, and since it runs only at the sleep, a worktree a shell kept stays until the child sleeps again, the clean-up after its branch's PR or *Clean up now* removes it, or the child is deleted; those last three close the child's shells as they do any thread's. A worktree whose `HEAD` has no commit since the one it started at (`baseOid` in `worktrees.json`, the parent's commit for a `worktree` child) has only its changes to lose, so origin is not fetched; one with commits stays while origin lacks one of them. Every other clean-up, and the checks of a delete with the box, measure a worktree the same way, so a child that holds only its parent's unpushed commits is not kept for them. A worktree that may go is removed by `session_cleanup_command`, whatever `session_cleanup_mode` says, the branch and the thread stay, and a wake puts the worktree back. Anything else keeps the worktree for the PR's clean-up: the log has the reason, only when it differs from the one the child's last sleep logged, and the row is not marked kept. A child in its parent's folder has no worktree of its own and loses nothing. Every run lands in `cleanups.json`, which the Stats view lists newest first as `Removed <what>` or, in the danger colour, `Kept: <reason>`; the title of a card's clean-up mark says `Kept: <reason>` too.

**Browser.** One Chromium browser per project, on its own profile and a fixed DevTools port saved in `browser-port`; one window per session. The window has one tab, labelled `[<project> · <n> <session title>]` in its title; the `browser` tool's `open`, `screenshot` and `close` make and act on it. A tab the page itself opens joins the window, out of agent-browser's reach. The session drives the tab with `agent-browser`, which the app bundle carries in `Contents/Helpers` (`AGENTOS_AGENT_BROWSER` to change) and puts first on the session's PATH; without it a session starts with no browser. Its environment names its own agent-browser session, the project's DevTools port and a pinned tab. agentos writes agent-browser's binding file, `<token>.target` in `~/.local/share/agentos/agent-browser/`, itself: to the session's tab when its window opens and to no tab when it closes, stopping the session's agent-browser daemon first, since the daemon reads the file only when it starts. agent-browser's own ways to pick a tab bring Chrome in front of the owner's windows. A command before the window opens fails, with `tab_gone` when another session's window is open, and never drives another session's tab. Claude may run `agent-browser` without asking (`Bash(agent-browser:*)`), at every access. A dialog nobody answers for 5 seconds is dismissed, because it blocks every later call. A DevTools connection the browser drops, as after the Mac slept, is made again and the sessions' pages attached again; a browser of this app left running on its port is reconnected at the next start and its windows matched to sessions by their labels, and only one that does not answer on its port is ended as a stray.

**Servers.** Claude Code runs each Bash call in a session of its own, so a server a thread starts leaves Claude's process group and outlives its tmux session. Every process the agent starts inherits its environment, so the thread's processes are those whose environment holds exactly `AGENTOS_SESSION=<the thread's id>` and `AGENTOS_CONTROL=<this app's control socket>` (`internal/procs` reads it with `sysctl kern.procargs2`); nothing else names them, never a name, folder, command or port, so a server the owner started, one in the shell drawer (whose shells get `AGENTOS_PROJECT` but no `AGENTOS_SESSION`) and another app's thread are never one. macOS shows no one the environment of its own programs in `/bin` and `/usr/bin`, so a server run by one of those is not found. A thread's servers are its processes that listen on TCP (`lsof -nP -iTCP -sTCP:LISTEN -F pn`), without its host and Claude, the host's child. The thread's Details view shows a Servers tab while it has one: a row per port, `localhost:<port>` and the short command, which opens `http://localhost:<port>` in the default browser (`OpenServer`, through `open`, built from the port alone), with a button that stops it (`StopServer(id, pid)`, which stops `pid` only once it finds it among the thread's servers again). `Servers(id)` lists them for a thread the app knows; the view reads it when it opens and at each turn end of the thread, and every 5 s only while the Servers tab is the one shown. Settle stops the thread's servers once the tmux session is gone. The app also stops them when it sees the thread's tmux session go any other way, as when Claude ends by itself, Delete stops any left before it removes the host socket, and the app at its start stops those of every settled thread its state knows each of these unless the thread's host answers on its socket (it runs under another app on the same state folder); a process of a thread the app does not know is never stopped. To stop a server the app checks again that its pid has the marker and the same start time, sends SIGTERM to its process group when every process in the group has the marker, else, when the group holds neither the host nor Claude, to each process of the group with the marker, one by one, so a supervisor that would start it again stops too, else to the server alone; it logs a line for each and returns, and SIGKILL goes after 5 s to what is left. Settle has always stopped Claude itself with SIGTERM, after which Claude ends its `run_in_background` tasks; a Settle for a change of access does not stop the servers, since the thread starts again at once. A thread that goes while no app runs keeps its servers until the app's next start.

**Everything else.** Notes (`notes`, filed as issues with `## Description`), evidence an agent files with `show` or a screenshot (`evidence`), the interruption tally and the activity ledger, both read from the event log (`stats`), a weekly digest of what changed in the project's dependencies, run by a locked-down `claude` with `internal/prompts/digest.md`, whose reply ends in the items as a JSON array that the app reads (`digest`), self-update from GitHub releases (`update`), holding off idle sleep while a session works (`awake`) and the settings panel (`settings`). The config file and the command line are in `docs/config.md`.

**Storage.** Notes, note images, evidence, the event log (all stats) and the digest live in `data_dir` (default `~/.local/share/agentos`), per project. PR tracking, the clean-up log, the record of the worktrees agentos made (`worktrees.json`), the browser profile, session temp folders, handovers, chat logs (`chats/<token>.jsonl`), chat images (`chat-media/<token>/`, kept at a wake, copied to a fork, removed at a delete), how far each session's transcripts were read and the slash commands a thread of the project reported last, for Home (`commands.json`), are always under `~/.local/share/agentos/<key>/`. State files, sockets (a host's is `hosts/<hash>/<token>.sock`, where `<hash>` is the first 8 hex characters of the project key's SHA-256, so the path's length does not depend on the project's name, in a folder only the owner can open), the tmux config and the last project are in `~/.local/state/agentos`. Every file is written to a temp file and renamed into place, except the event log: its lines are appended, since iCloud uploads a changed file whole. Each Mac writes only its own event files, named with its id from `machine-id` in the state folder, so a shared `data_dir` never has two Macs writing one file; the ledger re-reads the files that changed.

## Code

- Go: plain, small packages, injected runners (`gh`, `git`, `claude`) so tests never call the real thing. Each service has a `Service` struct for the front end and, when the CLI reaches it, a `Commands` struct. Tests sit beside the code and build the app with `apptest`. Comments only for a non-obvious why.
- Agent-facing texts live in `internal/prompts/*.md`, never inline in Go.
- Front end: one component per file, props typed inline as `{Name}Props`, early returns, every colour a token in `tokens.css`, one shared action registry drives shortcuts. Keep `types.ts` and `api.ts` in step with the Go `Service` structs, and `mock.ts` acting like the real thing. No new dependencies without a reason in the PR.
- Change `docs/config.md` in the same PR as a config key or command.
- Markdown is never hard-wrapped: each paragraph and each list item is one line.
- Minimal, clear UI: flat surfaces, colour only for meaning (state, issue type, focus).

## Workflow

Issues on `nednella/agentos` are the queue. One issue → branch `issue-<n>` in its own worktree, which agentos makes → one draft PR → the owner merges → the app cleans up. Conventional commits, one logical change each. Manual issues follow `.github/ISSUE_TEMPLATE/issue.md`: a `## Description` written by a human. A session never edits the issue body; it posts its plans and reviews as comments, a review headed `## Agent Review`.
