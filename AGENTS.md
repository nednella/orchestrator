# AGENTS.md

agentos: one desktop window for every coding-agent session. It shows which session needs the owner, the project's GitHub issues as a queue, notes, and each agent's chat. Agents keep running in a hidden tmux when the window closes.

## Hard rules

- Tests and manual checks run in an isolated setup: always set `AGENTOS_TMUX_SOCKET`, `AGENTOS_STATE_DIR`, `AGENTOS_DEV_DATA_DIR` and `AGENTOS_CONFIG` to throwaway values. The default socket holds the owner's live sessions; a test on it has killed them twice.
- Never install the app to `/Applications` or `~/Applications`, never run `make desktop-install`, `install.sh` or `agentos update` against the real home, unless the owner asks. Live sessions' hooks call the installed `agentos`, a link into the installed bundle.
- Stop only the processes you started, by their PID. Never `pkill`, `killall` or kill by a name pattern.
- Clean-up code deletes worktrees, and a configured `session_cleanup_command` may delete more. Any change to it ships with tests against throwaway git repos, never a real one.
- Never create a GitHub issue without the owner approving that specific issue.

## How it works

**One binary.** `desktop/` builds a Wails v2 app whose binary is also the `agentos` command: `~/.local/bin/agentos` links to `agentos.app/Contents/MacOS/agentos`, so the app, the command and the hooks are always one version. Typed at a terminal with no command, it opens the app; started with no terminal (Finder, `open`, the dock) it is the app.

**Sessions live in tmux.** Each agent runs in a tmux server on a private socket (`agentos` by default, `AGENTOS_TMUX_SOCKET` to change). A session's id is `<project key>/<8 random characters, a-z and 2-7>`. Closing the window leaves the agents running; the app finds them again when it starts. The front end shows each thread as its chat; only a shell's terminal attaches to its tmux pane, over `terminal.Service`. A Claude session's pane runs `agentos host --log <chat log> --socket <socket> -- claude …` with the app's own binary as `agentos`, not the one on PATH that the hooks call: the host runs Claude headless, keeps the session's chat log and serves a unix socket the app gives Claude its messages and interrupts through; the pane shows the host's echo of the chat, and Ctrl-C there interrupts Claude's turn. Each message gets a UUID, which the socket answers with and Claude echoes back (`--replay-user-messages`) when it takes the message in; it may carry PNG, JPEG, GIF or WebP images of at most 3.75 MB each, so their base64 stays under the API's 5 MB. While an approval waits, a message denies each waiting tool with its text, framed by `internal/prompts/denied.md`, as the reason and is not sent as a message. While a turn runs, a message is logged `queued` and written at once: Claude takes it in at the turn's next step, or runs it as a turn of its own after this one, and its echo logs it as the user's, so the host counts as busy until every written message has echoed and its turn has ended. Send now (`send_now`) is a plain interrupt, after which Claude runs the queued messages without their being sent again. A message that was queued when an interrupt went out and that Claude's reply to it does not list under `still_queued` leaves the queue, so it cannot keep the host busy, and is logged `unsent`. The first event the host logs for a run, before it listens on its socket or starts Claude, is `start`: the events before it are an earlier run's, also when that run's host was killed before it logged its `exit`. The host is busy while a turn runs, an approval waits or a queued message is still to run. The `hold` op (`host.Hold`) says whether it is idle and, when it is, holds it: every later send, answer and mode change is refused with `This thread is restarting` until it exits, so a restart that holds the host before it stops it loses no message, and the composer keeps the text of a refused one. The `mode` op (`host.SetMode`) changes Claude's permission mode between turns, to `plan` or `default` only: it is refused with `Change access when the turn ends` while the host is busy; otherwise it writes a `set_permission_mode` control request, waits up to 10 s for Claude's reply, logs a `mode` event with the new mode, and answers with Claude's own error when Claude refuses it. Claude also reports each change of its mode, its own included, on a `system` line of subtype `status` with `permissionMode`; the host logs that as a `mode` event when it is not the mode the log holds last. A reply to a control request of the host's other than the initialize and interrupt replies goes to the request that waits on it and is never logged. An answer to an approval can carry the input to allow the tool with, such as a question's answers; the log keeps that input on the `answer` event, so the chat can show the answers. A `result` that failed gives its `errors` as the `turn_end`'s text, which the chat shows as the turn's error without Claude's `[ede_diagnostic]` lines. A host started by an older build answers an op it does not know with an error, and a message with images sent to it returns an error, since it sends the text and drops the images. The app tags such a session `@agentos-hosted`, and keeps the mark in its state file once it ends. A session without the mark, live or ended, is an old terminal session: it ran in its pane before sessions ran under a host. Its row is `settled`, with the detail `Ran in a terminal before chats`, and the app leaves it as it is: it types nothing into it, never settles or cleans it up, follows no PR of it, and drops its hooks, so it raises no attention, wait or awake hold. `TypeInto` refuses it with `Thread <id> runs in an old terminal`, Settle with `Thread <id> runs in an old terminal; end it there`, Rename with `Thread <id> runs in an old terminal; it keeps its title`, and `agentos settle` without a number leaves it; starting its issue from the queue opens its row and starts nothing, so no second session claims its branch; and its chat with `This thread ran in a terminal before agentos showed chats`, which the thread view shows as its empty state. Archive refuses one that still runs with `Thread <id> runs in an old terminal; end it there`, so its row stays and no second thread claims its branch; once its pane has ended it archives like any settled thread. The chat service (`desktop/chat`) is the app's one subscriber to each live hosted session's host: it reads the chat log once, for the approvals that wait and the seq it ends at, subscribes after that seq, and when the stream ends while the session runs subscribes again after the last seq it had, waiting 100 ms, doubling to 2 s. Every live hosted session has its follower before the app takes its first call; the service checks the set every second, and `ChatWatch` starts a thread's follower when it has none and returns once that follower has read the log. It hands each `turn_end` to the sessions (see below), and each `mode`, with whether the owner allowed an `ExitPlanMode` approval just before it in that turn, to `Sessions.AccessChanged`; at its start, once the host listens or has had 10 s to, it reads the log and hands on the latest `mode` after the log's last `start`, none when that `start` has no `mode` after it, so a change made while the app was closed is followed too and an earlier run's is not. `AccessChanged` maps the mode (`plan` Read, `default` and `acceptEdits` Supervised, `bypassPermissions` Full) and records an access that is lower; a higher one only when it takes a Read thread to Supervised after an approved plan, so a Read thread whose plan the owner approves becomes Write · Supervised, and nothing Claude reports raises a thread to Full, sends `chat:pending` (`{id, pending}`, `pending` null once nothing waits) when the oldest unanswered approval of a session changes, and sends the events of each thread the front end watches, deltas among them, as `chat:<id>` (`{id, events}`), at most one per 33 ms per thread. `ChatHistory` reads the chat log, also of a settled session; the front end watches first, then reads the history, and merges the two by seq, since an event logged in between comes in both. Every other chat op on a settled session fails with `Thread <id> has settled`; an op the host refuses fails with the host's own reason (`host.Refused`), and one that cannot reach the host with `Thread <id> did not take …`, the cause going to the log. `ChatSend` takes a message's text and up to 10 images (png, jpeg, gif or webp, each at most `host.MaxImage`, 3.75 MB, whose base64 is the API's 5 MB), checks them all before it saves any, saves each as `<first 16 hex of its SHA-256>.<ext>` in the thread's `chat-media/<token>/` and sends their paths; the `user` event's `files` holds them, and `/media/<key>/chat-media/<token>/<file>` serves them. A host too old for images sends the text alone, and `ChatSend` returns that as a notice, not an error.

**Hooks report state.** A Claude session starts with `--settings` holding hooks that run `agentos hook <Event>`. The hook folds the event into the session's state file under a lock, then tells the app over the bus socket, `AGENTOS_SOCKET` (`~/.local/state/agentos/agentos.sock`); a missed send costs only a delay. From the events the app derives the session's state: `waiting` (a permission prompt, a question, or a reply that ends in a question), `working`, `idle` (the user's move) or `settled` (the process is gone; the row stays until archived, with no time limit). Settle, in a thread's right-click menu, `SettleThread` or `agentos settle`, stops the tmux session, whose host stops Claude. Archive, last in every thread's right-click menu and on a settled card (`ArchiveThread`), takes the thread off the list for good and keeps its history: a live thread is settled first, then its state file says `archived`, and it keeps that file, its chat log, chat images, handover, evidence and usage mark, while its temp folder, browser window and host socket go and the PR watch forgets it. An archived thread never comes back: a refresh, a restart and a late hook pass its state file over; Wake, `ChatSend`, `ChatDraft`, `TypeInto` and Settle refuse it with `Thread <id> is archived`; a PR command wakes nothing; and a start of its issue starts a new thread. Archive refuses a shell, and a shell's state file is never read. A state file that says `ended`, an older build's, shows as settled and is written back as `settled`. Claude Code runs no Stop hook after an interrupt, so the chat service also hands each `turn_end` from the session's host to the sessions, and at each start of the app the latest one in the chat log, so a turn interrupted while the app was closed ends too: a `turn_end` that comes while the session is still `working` or `waiting` from that turn goes into the state file as a Stop, so held prompts go out and the turn's usage is recorded; one with the error flag (an interrupt or an API error) goes in as a `TurnError`, which does the same but raises no reply alert. After the turn's Stop hook a `turn_end` changes nothing. The state file also keeps the latest 200 state changes, so the row's timeline and the `worked` time of stretches that ended while the app was closed outlive the app; a stretch is recorded once, at the change that ends it. The app writes what it started the session as (title, access, issue, action, model, effort, folder, branch, whether it runs under a host, the thread it was forked from, its first start `created` and its latest start `woke`) into the state file at start, at a wake and at a rename, and hooks keep it, so a session that ends while the app is closed comes back as itself. Each hook also reports the agent's working folder, which never changes the thread's branch. It also reports the transcript Claude Code writes: at each hook the app reads the new lines of it and of its subagents' transcripts and adds their tokens and cost, at the list prices in `internal/usage`, to the row. It records them as one `usage` event per model, for every access (an older build recorded a chat's as `chat_usage`, which the stats and the restart read still count), only when the turn is over: a second after Stop, since Claude Code writes the turn's last reply just after it, at SessionEnd and when the session is gone. After a restart it starts after the latest usage the event log holds for the session, so it reads again what it had not recorded; it starts each transcript at the offset it saved when it last recorded usage, so it does not read the whole file again. A woken thread keeps its id, so its usage goes on under it from its first start, and each wake records a start event labelled `resumed`. A start event an older build wrote for a session that resumed another's conversation names that session (`from`), and its row adds what the event log holds for each session before it in that conversation; the log keeps each session's own usage. The same read sets the row's model and effort to the newest assistant line's, kept in the tmux session and the state file like the start choice, so the row follows a `/model` change. Every session runs `claude` with these hooks; when `agentos` is not on PATH no thread starts, since nothing could report its state, and the app logs it and shows a warning.

**What a session is started with.** Folder: a thread runs where it starts and never moves. An issue thread, whatever its access, and a Write thread start in a worktree agentos makes for them; a Read thread with no issue starts in the project folder, and the owner may pick either place for a thread with no issue (`NewThread`'s `place`, `worktree` or `project`); the setup session runs in the project folder. The worktree is `<project>/trees/<branch>`, kept out of the owner's `git status` by a `/trees/` line agentos adds once to `<git-common-dir>/info/exclude` (never a `.gitignore`), on the issue's branch (`session_branch_fallback`) or, with no issue, on a branch named from the title: lower case, a `-` for each run of other characters than a-z and 0-9, at most 40 characters cut at a `-`, `thread` when nothing is left, then `-2`, `-3`… while a local or origin branch has that name. A branch that exists, locally or on origin (fetched when this clone has no copy), is checked out as it is and never reset; a new one is made by `session_worktree_command` from the default branch on origin, fetched first, and the worktree is the one git then lists on the branch, wherever the command put it. A branch that a worktree already has checked out runs the thread in that worktree, which agentos does not record and so never removes; one that another thread, live or settled, works on is refused with `Thread <n> works on <branch>`. A project that is not a git repository runs every thread in its folder. Each worktree agentos made is recorded in `worktrees.json` with the base it started from, and marked with the thread's id in its own git folder (`agentos-thread`); a start that fails after its worktree was made removes that worktree, without `--force`, and only while it is still the one agentos made. The branch is tagged `@agentos-branch` and kept in the state file as `branch`; the row's `worktree` is the folder only when agentos made it. Environment: `AGENTOS_SESSION`, `AGENTOS_SOCKET`, `AGENTOS_ISSUE` for an issue session, and `TMPDIR` set to its own temp folder, removed at the clean-up or when the thread is archived, which the Claude provider also sets as `CLAUDE_CODE_TMPDIR`. Claude runs with `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-prompt-tool stdio`, with the thread's access as `--permission-mode` (Read `plan`, Write · Supervised `default`, Write · Full access `bypassPermissions`) and the same `--allowedTools` at every access (the `agentos` and `gh issue` commands that hand work on, and `agent-browser` when it has a browser), so the access is the only difference. The access is tagged `@agentos-access` and kept in the state file as `access`; the owner changes it between turns from the access chip in the thread's composer (`SetAccess`), which is disabled with `Change access when the turn ends` while a turn runs or an approval waits. The app asks the thread's host, not the hook state, and refuses with the same sentence while the host is busy, so a thread waiting on a reply that asks can change and one that was just sent a message cannot; it refuses an archived thread, an old terminal session and a blank access (`Pick an access level`). A settled thread keeps the new access for its next wake; a live one changes between Read and Supervised through its host's `mode` op, with the same host and Claude, and a change to or from Full holds the host (`hold` op), records the new access, settles the thread and wakes it with it under the same id, resuming its conversation, since Claude takes `bypassPermissions` only from its start; a wake that fails leaves the thread settled with the new access; a session an older build tagged `@agentos-chat`, or whose state file says `chat`, is Read, one with neither is Supervised, and one with an access this build does not know is Read. Claude also gets `permissions.additionalDirectories` for the app's folders, `--model` and `--effort` when something picks them (see `docs/config.md`), and `--append-system-prompt` with the texts in `internal/prompts`: `session.md` (where it runs and the `agentos` commands every thread may use), then `thread.md` (one text for every access: what Read, Write and Full allow, the branch rules and the `APPLICATION_PROMPT:` rule), `worktree.md` for a thread that starts in a worktree, also one a human made (the branch and folder, and that the thread never makes a worktree), `fork.md` for a fork (it has no branch of its own and never runs `agentos track`), `browser.md` when the project has a browser, and `handover.md` with the context another session passed to `agentos issue --prompt`; the session that sets a project up gets only `setup-brief.md`.

**The command talks to the app.** Most `agentos` commands go to the running app over the control socket (`control.sock`, beside the bus socket); each service that the command reaches registers a `Commands` struct on the `desktop/control` router in `desktop/internal/app`. The project is `AGENTOS_PROJECT` (the shell session), else the asking session's, else the current one. The hidden `agentos mcp` serves the orchestration tools to a thread and sends each call as `orchestrate` with the token in `AGENTOS_MCP_TOKEN`, which names the thread that acts.

**The front end talks to Go through Wails.** Each `desktop/<pkg>` binds one `Service`; React calls `window.go.<pkg>.Service.<Method>(...)`, which returns a Promise, and listens with `window.runtime.EventsOn(name, handler)`. `desktop/frontend/src/api.ts` wraps every call and `types.ts` mirrors the Go structs; the Go side is the reference. A failing method rejects with a short sentence for the user; empty lists are `[]`, never `null`. Lists of one project arrive as `{project, items}` events: drop one whose project is not the current one. A thread's chat events are named `chat:<id>`; `chatEvent(id)` in `api.ts` gives the name its type. `window.go` is missing under plain `vite dev`, and the front end runs on `mock.ts`. With `AGENTOS_HTTP=127.0.0.1:PORT` the binary serves the real front end in a browser, with a shim that turns calls into `POST /__call/<pkg>.Service/<Method>` (header `X-Agentos: 1`) and events into the stream `/__events`; it answers only its own listen address.

**The queue.** `issues.Service` lists the current project's open issues through `gh`, grouped by the project's `queue_sections`. Starting an issue opens a thread with the access its action sets (`access: read|supervised|full`, Supervised by default; a config whose action still sets the old `kind` does not load), titled `#<n> <title>` with the action's name as a badge, starts claude with the model and effort the action and the issue's `model:`/`effort:` labels pick, then sends the action's command: Claude's host gets it as a message once its socket listens. With `session_prompt_send: manual` the command is left as a draft in the chat. An issue has one thread, whatever its access: one with a live thread gets it back with nothing sent, whatever action is started, also when two starts come at once; one whose thread has settled (and is not archived, ran under a host and is not a fork) gets that thread woken, with its own access, a handover given to the start in place of the one it had, and sent the action's command; an issue missing from the cached list has the list read again once. *Set up project* in a project's right-click menu on the rail runs `SetUpProject` for that project: for a project with no `queue_sections` it fills a basic block (`project.SetUp`), then it starts a Supervised session briefed to write the repository side; one that has queue sections keeps its config and only gets the session. `DismissSetup` still saves `setup_dismissed`, but no part of the UI calls it any more.

**Pull requests.** Every thread with a branch follows its branch and PR, whatever its access. A thread's branch is the one agentos made its worktree on or the one it reported with `agentos track`, and nothing else: the folder its hooks run in never adds, takes or changes it, and a thread with no recorded branch (one in the project folder that never ran `agentos track`, a fork, or one started before agentos recorded branches) has no PR and no clean-up. No two threads that are not archived have one branch. `agentos track --branch <name>` refuses a fork, a Read thread (`A Read thread works on no branch`), the default branch and a branch another thread that is not archived has (`Thread <n> works on <branch>`); it tags the branch `@agentos-branch` and keeps it in the state file, and when the thread's own worktree has that branch checked out, its record in `worktrees.json` follows; then the app looks up the branch's PR. The app fetches every tracked PR every minute. Between those, each project with a session on a branch has a watcher: `gh webhook forward` by default, falling back to polling the PR list every `pr_poll_interval` with `If-None-Match`. A session's Stop hook also looks its branch's PR up at once, so a PR opened during a turn shows when the turn ends. Each fetch also reads with git where the session's branch stands: commits not on origin (not on the base when origin has no copy), uncommitted files, commits ahead of and behind the base on origin, and after a merge the commits the merged PR did not take; each `PostToolUse` reads it again, so the row follows the agent's work. A new comment or review that is not an approval, by anyone but the gh user, types `pr_review_command` into the session (each reply in a review thread is a review of its own), but not while the PR is a draft unless `pr_review_drafts` is set; failing checks on a new commit type `pr_checks_command`; a new commit that conflicts with the base types `pr_conflict_command`, found at the one-minute fetch, since a base that moves does not touch the PR. Claude gets each command as a message through its host, or as a draft in its chat at once when `session_prompt_send` is `manual`. A session that is working or waiting on the owner gets each command held for it once, in order, when its turn ends; a session that ends first, settled or cleaned up, loses them. A settled issue thread is woken for it (see **Waking**), then gets the command, sent unless `session_prompt_send` is `manual`; a thread whose issue has another live thread stays settled, and so does a settled thread with no issue. Prompts held for a thread that settles by itself go out after it wakes; a thread the owner or a clean-up settled loses them.

**Waking.** A settled thread that ran under a host wakes under its own id: *Wake* on its card or in its right-click menu (`WakeThread`), a message or a draft from its composer (`ChatSend` and `ChatDraft` wake it first), a PR command, or a start of its issue. `Sessions.Wake` starts a tmux session with the same name in the folder the thread started in, under a host that goes on with the same chat log at the same socket, so the chat's numbering has no gap, with `claude --resume <conversation>` when it has one, and the thread's model, effort, handover, browser and fork tag. The thread keeps its row, number, state file, history, usage and branch; `created` stays its first start, `woke` and the row's `wokeAt` move to the wake, and a PR that merged or closed before the wake is an earlier wake's. The wake also lifts a clean-up's mark, so its next PR is watched, settles it and is cleaned up. A thread that ran in a terminal before chats cannot be woken, nor can a live one.

**Forks.** *Fork from here* on a reply of a thread that runs, or ran, under a host calls `ForkSession(id, at)`, where `at` is the uuid of the reply's last block, and selects the new thread. Claude starts with `--resume <conversation> --fork-session --resume-session-at <uuid>`, so the fork continues the conversation up to that reply under a new id. The fork is titled `<title> (fork)`, has the thread's access, issue, model, effort and handover, and starts in the folder the thread runs in, its worktree too, since Claude finds a conversation by its folder, with no branch of its own. Before the fork's host starts, the app writes the fork's chat log: the thread's events up to that block, without drafts, queued or unsent messages and the thread's run starts, then a `turn_end` at the block's time; it copies the images those events show into the fork's `chat-media/<token>/`. On a message of the user's, the fork continues from the reply before it and gets the message's text as a draft in its composer. A thread with no conversation yet cannot be forked. A fork is tagged `@agentos-fork` with the thread's id, kept in its state file and at a wake, and its row's `forkOf` names the thread. Its issue is only shown: it claims no branch, `agentos track` refuses it, it is never the issue's session for the queue, a start or a wake, and it hears no PR. A live fork whose working folder is a worktree, or inside one, blocks the clean-up of that worktree with `Fork <title> still works in this worktree`; a forced clean-up goes ahead, and a settled fork blocks nothing. A uuid or a conversation Claude cannot find ends the fork's first turn with `error_during_execution`, and the chat shows Claude's reason.

**Clean-up.** Clean-up frees disk: it removes only the worktree agentos made for the thread, and the branch always stays. When the PR of a thread's branch merges or closes, the thread settles, whatever the clean-up mode. When the PR merges (`auto` by default) or closes (`manual` by default), the app cleans up: the checks first (a worktree in the middle of a rebase, changes or new files in it, commits on its HEAD that no ref on origin holds and the merged PR did not take, a live fork in it, or a worktree no longer on the thread's branch keeps it, with the reason; so does a failed fetch of origin), then it settles a live thread, runs the checks again, since the agent may have changed the worktree until it stopped, runs `session_cleanup_command` (default `git worktree remove {force} {worktree}`) through `sh -c` in the project folder, then removes the thread's temp folder and closes its browser window; its row, state file, chat log, images, evidence and branch stay. The command runs once per worktree, on the folder recorded in `worktrees.json`, and only while that folder still holds the worktree agentos made for the thread (the newest record at the path is the thread's and not removed, and the worktree's `agentos-thread` marker names it): never on the project folder, git's main worktree, a folder holding either, a worktree a human made (also one at a path agentos used before) or one a thread only ran in, forced or not. Before each step after the settle, just before the command and at the end, the app checks that the thread has not woken since the clean-up settled it, and stops, keeping what is left, with `Thread <n> woke during the clean-up` if it has, so a woken thread keeps its worktree, temp folder, browser window and PR; `CleaningUp(id)` says while a clean-up runs. The worktree counts as removed once git no longer lists it and its folder is gone, whatever the command's exit code, and a worktree whose folder is gone already counts too; its record then says `removed`, and no clean-up runs on it again. A command that fails and leaves it keeps it with `the clean-up command failed: <first line>`, and one that exits 0 and leaves it with `the clean-up command left <path>`. A thread with no worktree agentos made, or one removed already, loses only its temp folder and browser window; `manual` still asks first, since the app never cleans up by itself then. A kept worktree leaves the row `blocked` with the reason; the user can force it, which skips the checks but never the rules on what agentos made. A clean-up that finished is not run again for that thread, also after a restart (`cleaned` in `prs.json`), and the row shows no PR. A PR that merged or closed before the thread last started, at its first start or its latest wake, is an earlier thread's, or an earlier wake's, and is ignored, unless the owner was asked to clean up after it and has not answered: that ask outlives a wake and a restart (`asked` in `prs.json`), and it settles nothing. `session_cleanup_mode` picks whether a merged or closed PR is cleaned up at once or asks first (`cleanup: 'ask'`), so a PR that opened and merged while the app was closed is cleaned up at the next start. Every run lands in `cleanups.json`.

**Browser.** One Chromium browser per project, on its own profile and a fixed DevTools port saved in `browser-port`; one window per session. The window has one tab, labelled `[<project> · <n> <session title>]` in its title; `agentos browser open|screenshot|close` make and act on it. A tab the page itself opens joins the window, out of agent-browser's reach. The session drives the tab with `agent-browser`, which the app bundle carries in `Contents/Helpers` (`AGENTOS_AGENT_BROWSER` to change) and puts first on the session's PATH; without it a session starts with no browser. Its environment names its own agent-browser session, the project's DevTools port and a pinned tab. agentos writes agent-browser's binding file, `<token>.target` in `~/.local/share/agentos/agent-browser/`, itself: to the session's tab when its window opens and to no tab when it closes, stopping the session's agent-browser daemon first, since the daemon reads the file only when it starts. agent-browser's own ways to pick a tab bring Chrome in front of the owner's windows. A command before the window opens fails, with `tab_gone` when another session's window is open, and never drives another session's tab. Claude may run `agent-browser` without asking (`Bash(agent-browser:*)`), at every access. A dialog nobody answers for 5 seconds is dismissed, because it blocks every later call. A DevTools connection the browser drops, as after the Mac slept, is made again and the sessions' pages attached again; a browser of this app left running on its port is reconnected at the next start and its windows matched to sessions by their labels, and only one that does not answer on its port is ended as a stray.

**Everything else.** Notes (`notes`, filed as issues with `## Description`), evidence an agent files with `agentos show` or a screenshot (`evidence`), the interruption tally and the activity ledger, both read from the event log (`stats`), a weekly digest of what changed in the project's dependencies, run by a locked-down `claude` with `internal/prompts/digest.md` (`digest`), self-update from GitHub releases (`update`), holding off idle sleep while a session works (`awake`) and the settings panel (`settings`). The config file and the command line are in `docs/config.md`.

**Storage.** Notes, note images, evidence, the event log (all stats) and the digest live in `data_dir` (default `~/.local/share/agentos`), per project. PR tracking, the clean-up log, the record of the worktrees agentos made (`worktrees.json`), the browser profile, session temp folders, handovers, chat logs (`chats/<token>.jsonl`), chat images (`chat-media/<token>/`, kept at a wake and an archive, copied to a fork) and how far each session's transcripts were read are always under `~/.local/share/agentos/<key>/`. State files, sockets (a host's is `hosts/<hash>/<token>.sock`, where `<hash>` is the first 8 hex characters of the project key's SHA-256, so the path's length does not depend on the project's name, in a folder only the owner can open), the tmux config and the last project are in `~/.local/state/agentos`. Every file is written to a temp file and renamed into place, except the event log: its lines are appended, since iCloud uploads a changed file whole. Each Mac writes only its own event files, named with its id from `machine-id` in the state folder, so a shared `data_dir` never has two Macs writing one file; the ledger re-reads the files that changed.

## Code

- Go: plain, small packages, injected runners (`gh`, `git`, `claude`) so tests never call the real thing. Each service has a `Service` struct for the front end and, when the CLI reaches it, a `Commands` struct. Tests sit beside the code and build the app with `apptest`. Comments only for a non-obvious why.
- Agent-facing texts live in `internal/prompts/*.md`, never inline in Go.
- Front end: one component per file, props typed inline as `{Name}Props`, early returns, every colour a token in `tokens.css`, one shared action registry drives shortcuts and the command line. Keep `types.ts` and `api.ts` in step with the Go `Service` structs, and `mock.ts` acting like the real thing. No new dependencies without a reason in the PR.
- Change `docs/config.md` in the same PR as a config key or command.
- Markdown is never hard-wrapped: each paragraph and each list item is one line.
- Minimal, clear UI: flat surfaces, colour only for meaning (state, issue type, focus).

## Workflow

Issues on `nednella/agentos` are the queue. One issue → branch `issue-<n>` in its own worktree, which agentos makes → one draft PR → the owner merges → the app cleans up. Conventional commits, one logical change each. Manual issues follow `.github/ISSUE_TEMPLATE/issue.md`: a `## Description` written by a human. A session never edits the issue body; it posts its plans and reviews as comments, a review headed `## Agent Review`.
