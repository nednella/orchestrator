# AGENTS.md

agentos: one desktop window for every coding-agent session. It shows which session needs the owner, the project's GitHub issues as a queue, notes, and each agent's chat. Agents keep running in a hidden tmux when the window closes.

## Hard rules

- Tests and manual checks run in an isolated setup: always set `AGENTOS_TMUX_SOCKET`, `AGENTOS_STATE_DIR`, `AGENTOS_DEV_DATA_DIR` and `AGENTOS_CONFIG` to throwaway values. The default socket holds the owner's live sessions; a test on it has killed them twice.
- Never install the app to `/Applications` or `~/Applications`, never run `make desktop-install`, `install.sh` or `agentos update` against the real home, unless the owner asks. Live sessions' hooks call the installed `agentos`, a link into the installed bundle.
- Stop only the processes you started, by their PID. Never `pkill`, `killall` or kill by a name pattern.
- Clean-up code deletes worktrees and branches. Any change to it ships with tests against throwaway git repos, never a real one.
- Never create a GitHub issue without the owner approving that specific issue.

## How it works

**One binary.** `desktop/` builds a Wails v2 app whose binary is also the `agentos` command: `~/.local/bin/agentos` links to `agentos.app/Contents/MacOS/agentos`, so the app, the command and the hooks are always one version. Typed at a terminal with no command, it opens the app; started with no terminal (Finder, `open`, the dock) it is the app.

**Sessions live in tmux.** Each agent runs in a tmux server on a private socket (`agentos` by default, `AGENTOS_TMUX_SOCKET` to change). A session's id is `<project key>/<8 random characters, a-z and 2-7>`. Closing the window leaves the agents running; the app finds them again when it starts. The front end shows each thread as its chat; only a shell's terminal attaches to its tmux pane, over `terminal.Service`. A Claude session's pane runs `agentos host --log <chat log> --socket <socket> -- claude …` with the app's own binary as `agentos`, not the one on PATH that the hooks call: the host runs Claude headless, keeps the session's chat log and serves a unix socket the app gives Claude its messages and interrupts through; the pane shows the host's echo of the chat, and Ctrl-C there interrupts Claude's turn. Each message gets a UUID, which the socket answers with and Claude echoes back (`--replay-user-messages`) when it takes the message in; it may carry PNG, JPEG, GIF or WebP images of at most 3.75 MB each, so their base64 stays under the API's 5 MB. While an approval waits, a message denies each waiting tool with its text, framed by `internal/prompts/denied.md`, as the reason and is not sent as a message. While a turn runs, a message is logged `queued` and written at once: Claude takes it in at the turn's next step, or runs it as a turn of its own after this one, and its echo logs it as the user's, so the host counts as busy until every written message has echoed and its turn has ended. Send now (`send_now`) is a plain interrupt, after which Claude runs the queued messages without their being sent again. A message that was queued when an interrupt went out and that Claude's reply to it does not list under `still_queued` leaves the queue, so it cannot keep the host busy, and is logged `unsent`. An answer to an approval can carry the input to allow the tool with, such as a question's answers; the log keeps that input on the `answer` event, so the chat can show the answers. A `result` that failed gives its `errors` as the `turn_end`'s text, which the chat shows as the turn's error without Claude's `[ede_diagnostic]` lines. A host started by an older build answers an op it does not know with an error, and a message with images sent to it returns an error, since it sends the text and drops the images. The app tags such a session `@agentos-hosted`, and keeps the mark in its state file once it ends. A session without the mark, live or ended, is an old terminal session: it ran in its pane before sessions ran under a host. Its row is `settled`, with the detail `Ran in a terminal before chats`, and the app leaves it as it is: it types nothing into it, never settles or cleans it up, follows no PR of it, and drops its hooks, so it raises no attention, wait or awake hold. `TypeInto` refuses it with `Thread <id> runs in an old terminal`, Settle with `Thread <id> runs in an old terminal; end it there`, Rename with `Thread <id> runs in an old terminal; it keeps its title`, and `agentos settle` without a number leaves it; starting its issue from the queue opens its row and starts nothing, so no second session claims its branch; and its chat with `This thread ran in a terminal before agentos showed chats`, which the thread view shows as its empty state. Dismissing one that still runs only hides its row. The chat service (`desktop/chat`) is the app's one subscriber to each live hosted session's host: it reads the chat log once, for the approvals that wait and the seq it ends at, subscribes after that seq, and when the stream ends while the session runs subscribes again after the last seq it had, waiting 100 ms, doubling to 2 s. Every live hosted session has its follower before the app takes its first call; the service checks the set every second, and `ChatWatch` starts a thread's follower when it has none and returns once that follower has read the log. It hands each `turn_end` to the sessions (see below), sends `chat:pending` (`{id, pending}`, `pending` null once nothing waits) when the oldest unanswered approval of a session changes, and sends the events of each thread the front end watches, deltas among them, as `chat:<id>` (`{id, events}`), at most one per 33 ms per thread. `ChatHistory` reads the chat log, also of a settled session; the front end watches first, then reads the history, and merges the two by seq, since an event logged in between comes in both. Every other chat op on a settled session fails with `Thread <id> has settled`; an op the host refuses fails with the host's own reason (`host.Refused`), and one that cannot reach the host with `Thread <id> did not take …`, the cause going to the log. `ChatSend` takes a message's text and up to 10 images (png, jpeg, gif or webp, each at most `host.MaxImage`, 3.75 MB, whose base64 is the API's 5 MB), checks them all before it saves any, saves each as `<first 16 hex of its SHA-256>.<ext>` in the thread's `chat-media/<token>/` and sends their paths; the `user` event's `files` holds them, and `/media/<key>/chat-media/<token>/<file>` serves them. A host too old for images sends the text alone, and `ChatSend` returns that as a notice, not an error.

**Hooks report state.** A Claude session starts with `--settings` holding hooks that run `agentos hook <Event>`. The hook folds the event into the session's state file under a lock, then tells the app over the bus socket, `AGENTOS_SOCKET` (`~/.local/state/agentos/agentos.sock`); a missed send costs only a delay. From the events the app derives the session's state: `waiting` (a permission prompt, a question, or a reply that ends in a question), `working`, `idle` (the user's move) or `settled` (the process is gone; the row stays until dismissed, with no time limit). Settle, in a thread's right-click menu, `SettleThread` or `agentos settle`, stops the tmux session, whose host stops Claude. A state file that says `ended`, an older build's, shows as settled and is written back as `settled`. Claude Code runs no Stop hook after an interrupt, so the chat service also hands each `turn_end` from the session's host to the sessions, and at each start of the app the latest one in the chat log, so a turn interrupted while the app was closed ends too: a `turn_end` that comes while the session is still `working` or `waiting` from that turn goes into the state file as a Stop, so held prompts go out and the turn's usage is recorded; one with the error flag (an interrupt or an API error) goes in as a `TurnError`, which does the same but raises no reply alert. After the turn's Stop hook a `turn_end` changes nothing. The state file also keeps the latest 200 state changes, so the row's timeline and the `worked` time of stretches that ended while the app was closed outlive the app; a stretch is recorded once, at the change that ends it. The app writes what it started the session as (title, chat or task, issue, action, model, effort, folder, whether it runs under a host, the thread it was forked from, its first start `created` and its latest start `woke`) into the state file at start, at a wake and at a rename, and hooks keep it, so a session that ends while the app is closed comes back as itself. Each hook also reports the agent's working folder, from which the app reads the branch it works on. It also reports the transcript Claude Code writes: at each hook the app reads the new lines of it and of its subagents' transcripts and adds their tokens and cost, at the list prices in `internal/usage`, to the row. It records them as one `usage` event per model (`chat_usage` for a chat) only when the turn is over: a second after Stop, since Claude Code writes the turn's last reply just after it, at SessionEnd and when the session is gone. After a restart it starts after the latest usage the event log holds for the session, so it reads again what it had not recorded; it starts each transcript at the offset it saved when it last recorded usage, so it does not read the whole file again. A woken thread keeps its id, so its usage goes on under it from its first start, and each wake records a start event labelled `resumed`. A start event an older build wrote for a session that resumed another's conversation names that session (`from`), and its row adds what the event log holds for each session before it in that conversation; the log keeps each session's own usage. The same read sets the row's model and effort to the newest assistant line's, kept in the tmux session and the state file like the start choice, so the row follows a `/model` change. Every session runs `claude` with these hooks; when `agentos` is not on PATH no thread starts, since nothing could report its state, and the app logs it and shows a warning.

**What a session is started with.** Environment: `AGENTOS_SESSION`, `AGENTOS_SOCKET`, `AGENTOS_ISSUE` for an issue session, and `TMPDIR` set to its own temp folder, removed at the clean-up or when the row is dismissed, which the Claude provider also sets as `CLAUDE_CODE_TMPDIR`. Claude runs with `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-prompt-tool stdio`, and also gets `permissions.additionalDirectories` for the app's folders, `--model` and `--effort` when something picks them (see `docs/config.md`), and `--append-system-prompt` with the texts in `internal/prompts`: `session.md` (where it runs and the `agentos` commands every thread may use), then `thread.md` (one text for every access: what Read, Write and Full allow, the branch rules and the `APPLICATION_PROMPT:` rule), `fork.md` for a fork (it has no branch of its own and never runs `agentos track`), `browser.md` when the project has a browser, and `handover.md` with the context another session passed to `agentos issue --prompt`; the session that sets a project up gets only `setup-brief.md`.

**The command talks to the app.** Most `agentos` commands go to the running app over the control socket (`control.sock`, beside the bus socket); each service that the command reaches registers a `Commands` struct on the `desktop/control` router in `desktop/internal/app`. The project is `AGENTOS_PROJECT` (the shell session), else the asking session's, else the current one.

**The front end talks to Go through Wails.** Each `desktop/<pkg>` binds one `Service`; React calls `window.go.<pkg>.Service.<Method>(...)`, which returns a Promise, and listens with `window.runtime.EventsOn(name, handler)`. `desktop/frontend/src/api.ts` wraps every call and `types.ts` mirrors the Go structs; the Go side is the reference. A failing method rejects with a short sentence for the user; empty lists are `[]`, never `null`. Lists of one project arrive as `{project, items}` events: drop one whose project is not the current one. A thread's chat events are named `chat:<id>`; `chatEvent(id)` in `api.ts` gives the name its type. `window.go` is missing under plain `vite dev`, and the front end runs on `mock.ts`. With `AGENTOS_HTTP=127.0.0.1:PORT` the binary serves the real front end in a browser, with a shim that turns calls into `POST /__call/<pkg>.Service/<Method>` (header `X-Agentos: 1`) and events into the stream `/__events`; it answers only its own listen address.

**The queue.** `issues.Service` lists the current project's open issues through `gh`, grouped by the project's `queue_sections`. Starting an issue opens a task, or a chat for an action with `kind: chat`, titled `#<n> <title>` with the action's name as a badge, starts claude with the model and effort the action and the issue's `model:`/`effort:` labels pick, then sends the action's command: Claude's host gets it as a message once its socket listens. With `session_prompt_send: manual` the command is left as a draft in the chat. An issue with a live session of that kind gets that session back with nothing sent, also when two starts come at once; one whose thread of that kind has settled (and is not archived, ran under a host and is not a fork) gets that thread woken and sent the action's command, so an issue keeps one thread; an issue missing from the cached list has the list read again once. *Set up project* in a project's right-click menu on the rail runs `SetUpProject` for that project: for a project with no `queue_sections` it fills a basic block (`project.SetUp`), then it starts a session briefed to write the repository side; one that has queue sections keeps its config and only gets the session. `DismissSetup` still saves `setup_dismissed`, but no part of the UI calls it any more.

**Pull requests.** A session with an issue works on the issue's branch: the one it reported with `agentos track`, else the one checked out in its working folder, else the project's `session_branch_fallback`. A session without one collects every branch it was seen on (other repos, a detached head and the default branch are ignored; in the project folder itself, not a linked worktree, only a branch that one of its own tool calls switched to, so the owner's checkout there is never its own), remembered in `prs.json`; its PR is the one on its newest branch that has one. A session owns the branches it reported with `agentos track`, which refuses the default branch, and its issue's `session_branch_fallback`, which it claims when it starts; a branch it only saw in its folder is not its own. Owning a branch takes it from each session that only saw it, so a task that hands work on moves it to the new issue's branch and leaves it, and the new task's `agentos track` makes it that task's. A working folder alone does not add a branch another session works on now or owns, and one a session worked on before that another session works on now is left out of its clean-up. The app fetches every tracked PR every minute. Between those, each project with a session on a branch has a watcher: `gh webhook forward` by default, falling back to polling the PR list every `pr_poll_interval` with `If-None-Match`. A session's Stop hook also looks its branch's PR up at once, so a PR opened during a turn shows when the turn ends. Each fetch also reads with git where the session's branch stands: commits not on origin (not on the base when origin has no copy), uncommitted files, commits ahead of and behind the base on origin, and after a merge the commits the merged PR did not take; each `PostToolUse` reads it again, so the row follows the agent's work. A new comment or review that is not an approval, by anyone but the gh user, types `pr_review_command` into the session (each reply in a review thread is a review of its own), but not while the PR is a draft unless `pr_review_drafts` is set; failing checks on a new commit type `pr_checks_command`; a new commit that conflicts with the base types `pr_conflict_command`, found at the one-minute fetch, since a base that moves does not touch the PR. When several sessions list a PR's branch, only one hears the PR, its commands and its opened alert: one that owns the branch, then a live one, then one on the branch now. Claude gets each command as a message through its host, or as a draft in its chat at once when `session_prompt_send` is `manual`. A session that is working or waiting on the owner gets each command held for it once, in order, when its turn ends; a session that ends first, settled or cleaned up, loses them. A settled issue thread is woken for it (see **Waking**), then gets the command, sent unless `session_prompt_send` is `manual`; a thread whose issue has another live thread stays settled, and so does a settled thread with no issue. Prompts held for a thread that settles by itself go out after it wakes; a thread the owner or a clean-up settled loses them.

**Waking.** A settled thread that ran under a host wakes under its own id: *Wake* on its card or in its right-click menu (`WakeThread`), a message or a draft from its composer (`ChatSend` and `ChatDraft` wake it first), a PR command, or a start of its issue. `Sessions.Wake` starts a tmux session with the same name in the folder the thread started in, under a host that goes on with the same chat log at the same socket, so the chat's numbering has no gap, with `claude --resume <conversation>` when it has one, and the thread's model, effort, handover, browser and fork tag. The thread keeps its row, number, state file, history, usage and branches; `created` stays its first start, `woke` and the row's `wokeAt` move to the wake, and a PR that merged or closed before the wake is an earlier wake's. The wake also lifts a clean-up's mark, so its next PR is watched, settles it and is cleaned up. A thread that ran in a terminal before chats cannot be woken, nor can a live one.

**Forks.** *Fork from here* on a reply of a thread that runs, or ran, under a host calls `ForkSession(id, at)`, where `at` is the uuid of the reply's last block, and selects the new thread. Claude starts with `--resume <conversation> --fork-session --resume-session-at <uuid>`, so the fork continues the conversation up to that reply under a new id. The fork is titled `<title> (fork)`, has the thread's kind, issue, model, effort and handover, and starts in the project folder, as the thread did. Before the fork's host starts, the app writes the fork's chat log: the thread's events up to that block, without drafts and queued or unsent messages, then a `turn_end` at the block's time; it copies the images those events show into the fork's `chat-media/<token>/`. On a message of the user's, the fork continues from the reply before it and gets the message's text as a draft in its composer. A thread with no conversation yet cannot be forked. A fork is tagged `@agentos-fork` with the thread's id, kept in its state file and at a wake, and its row's `forkOf` names the thread. Its issue is only shown: it claims no branch, `agentos track` refuses it, it is never the issue's session for the queue, a start or a wake, and it hears no PR. A live fork whose working folder is a worktree, or inside one, blocks the clean-up of that worktree with `Fork <title> still works in this worktree`; a forced clean-up goes ahead, and a settled fork blocks nothing. A uuid or a conversation Claude cannot find ends the fork's first turn with `error_during_execution`, and the chat shows Claude's reason.

**Clean-up.** When the PR of the branch a thread works on now merges or closes after the thread saw it open, the thread that hears it settles, whatever the clean-up mode. When a session's PR merges (`auto` by default) or closes (`manual` by default), the app cleans up: safety checks first (no changes in the worktree, no commits missing from origin or, for a merged PR whose branch is gone, from the merged commit), then `session_cleanup_command` once per branch through `sh -c` in the project folder, then it removes the session's temp folder and closes its browser window, and the thread settles; its row, state file, chat log, images and evidence stay. A clean-up that finished is not run again for that thread, also after a restart (`cleaned` in `prs.json`), and the row shows no PR. A branch the session only saw is cleaned up only if the session saw its PR open: a merged or closed PR it never saw open takes the branch from the session and leaves the session running, and a seen branch with no PR is never cleaned up. A worktree in the middle of a rebase blocks the clean-up. A PR on a branch the session moved on from cleans up only that branch, and the session goes on; another branch with an open PR blocks the session's own clean-up. A failed check or command leaves the row `blocked` with the reason; the user can force it. A PR that merged or closed before the thread last started, at its first start or its latest wake, is an earlier thread's, or an earlier wake's, and is ignored. A PR first seen already merged or closed sets `cleanup: 'ask'`. Every run lands in `cleanups.json`.

**Browser.** One Chromium browser per project, on its own profile and a fixed DevTools port saved in `browser-port`; one window per session. The window has one tab, labelled `[<project> · <n> <session title>]` in its title; `agentos browser open|screenshot|close` make and act on it. A tab the page itself opens joins the window, out of agent-browser's reach. The session drives the tab with `agent-browser`, which the app bundle carries in `Contents/Helpers` (`AGENTOS_AGENT_BROWSER` to change) and puts first on the session's PATH; without it a session starts with no browser. Its environment names its own agent-browser session, the project's DevTools port and a pinned tab. agentos writes agent-browser's binding file, `<token>.target` in `~/.local/share/agentos/agent-browser/`, itself: to the session's tab when its window opens and to no tab when it closes, stopping the session's agent-browser daemon first, since the daemon reads the file only when it starts. agent-browser's own ways to pick a tab bring Chrome in front of the owner's windows. A command before the window opens fails, with `tab_gone` when another session's window is open, and never drives another session's tab. Claude may run `agent-browser` without asking (`Bash(agent-browser:*)`), a chat in plan mode too. A dialog nobody answers for 5 seconds is dismissed, because it blocks every later call. A DevTools connection the browser drops, as after the Mac slept, is made again and the sessions' pages attached again; a browser of this app left running on its port is reconnected at the next start and its windows matched to sessions by their labels, and only one that does not answer on its port is ended as a stray.

**Everything else.** Notes (`notes`, filed as issues with `## Description`), evidence an agent files with `agentos show` or a screenshot (`evidence`), the interruption tally and the activity ledger, both read from the event log (`stats`), a weekly digest of what changed in the project's dependencies, run by a locked-down `claude` with `internal/prompts/digest.md` (`digest`), self-update from GitHub releases (`update`), holding off idle sleep while a session works (`awake`) and the settings panel (`settings`). The config file and the command line are in `docs/config.md`.

**Storage.** Notes, note images, evidence, the event log (all stats) and the digest live in `data_dir` (default `~/.local/share/agentos`), per project. PR tracking, the clean-up log, the browser profile, session temp folders, handovers, chat logs (`chats/<token>.jsonl`), chat images (`chat-media/<token>/`, kept at a wake, copied to a fork, removed with the row) and how far each session's transcripts were read are always under `~/.local/share/agentos/<key>/`. State files, sockets (a host's is `hosts/<hash>/<token>.sock`, where `<hash>` is the first 8 hex characters of the project key's SHA-256, so the path's length does not depend on the project's name, in a folder only the owner can open), the tmux config and the last project are in `~/.local/state/agentos`. Every file is written to a temp file and renamed into place, except the event log: its lines are appended, since iCloud uploads a changed file whole. Each Mac writes only its own event files, named with its id from `machine-id` in the state folder, so a shared `data_dir` never has two Macs writing one file; the ledger re-reads the files that changed.

## Code

- Go: plain, small packages, injected runners (`gh`, `git`, `claude`) so tests never call the real thing. Each service has a `Service` struct for the front end and, when the CLI reaches it, a `Commands` struct. Tests sit beside the code and build the app with `apptest`. Comments only for a non-obvious why.
- Agent-facing texts live in `internal/prompts/*.md`, never inline in Go.
- Front end: one component per file, props typed inline as `{Name}Props`, early returns, every colour a token in `tokens.css`, one shared action registry drives shortcuts and the command line. Keep `types.ts` and `api.ts` in step with the Go `Service` structs, and `mock.ts` acting like the real thing. No new dependencies without a reason in the PR.
- Change `docs/config.md` in the same PR as a config key or command.
- Markdown is never hard-wrapped: each paragraph and each list item is one line.
- Minimal, clear UI: flat surfaces, colour only for meaning (state, issue type, focus).

## Workflow

Issues on `nednella/agentos` are the queue. One issue → branch `issue-<n>` in its own worktree → one draft PR → the owner merges → the app cleans up. Conventional commits, one logical change each. Manual issues follow `.github/ISSUE_TEMPLATE/issue.md`: a `## Description` written by a human. A session never edits the issue body; it posts its plans and reviews as comments, a review headed `## Agent Review`.
